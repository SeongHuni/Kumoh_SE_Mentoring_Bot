# 학과 챗봇 RAG — 2차 발표

**발표 시간 기준:** 15~20분
**총 슬라이드:** 12장

**발표 흐름**

| 부 | 주제 | 슬라이드 |
| --- | --- | --- |
| 0 | 표지 · 개요 | 1 |
| 1 | 평가 데이터셋 | 2 |
| 2 | Overlap 전략 검증 | 3–6 |
| 3 | 리랭킹 전략 검증 | 7–9 |
| 4 | 다음 단계 — 프롬프트 전략 | 10–11 |
| — | 결론 | 12 |

## 슬라이드 1

**제목:** 청킹 이후 — Overlap과 리랭킹을 검증했다

**핵심 메시지:** RAG의 대표적 관행 두 가지를 실제로 적용하고 측정한 결과, 둘 다 채택하지 않기로 했다

**데이터:**

| 순서 | 내용 |
| ---: | --- |
| 1 | 평가에 사용한 정답 데이터셋 |
| 2 | Overlap 전략 — 적용 결과와 미채택 사유 |
| 3 | 리랭킹 전략 — 3개 모델 비교 결과 |
| 4 | 다음 단계 — 프롬프트 전략 | 

**시각화:** 목차를 4개 카드로 가로 배치. 각 카드에 번호(01~04)와 제목만.

**발표 노트:**
- 1차 발표에서 10개 청킹 전략을 비교해 `fixed-size 500 tokens`를 채택했다
- 2차는 그 위에 얹는 두 가지 기법을 검증한 결과다
- 결론부터 말하면 둘 다 쓰지 않기로 했고, 오늘은 그 근거를 설명한다

## 슬라이드 2

**제목:** 평가에 사용한 정답 데이터셋

**핵심 메시지:** 질문 · 정답 문서 · 근거 · 채점 기준을 갖춘 골든셋으로 모든 전략을 평가했다

**데이터 — 데이터셋 예시 (슬라이드에 코드 블록으로 표시):**

```json
{
  "question": "2025-2학기 수강지도 상담 기간은 언제인가요?",
  "gold_doc_ids": ["kumoh-notice-44578"],
  "gold_category": "수업",
  "expected_evidence": [
    "2025-2학기 수강지도 상담 기간 : 7. 28.(월) 09:00 ~ 8. 6.(수) 18:00까지"
  ],
  "answer_checkpoints": [
    "상담 기간 시작일과 종료일",
    "상담 기간의 시간"
  ],
  "question_type": "단일사실"
}
```

**데이터 — 필드 설명:**

| 필드 | 역할 |
| --- | --- |
| `question` | 사용자가 던지는 질문 |
| `gold_doc_ids` | 이 질문의 정답이 들어있는 문서 ID |
| `expected_evidence` | 답변에 반드시 포함돼야 할 근거 |
| `answer_checkpoints` | 답변 채점 기준 |
| `question_type` | 단일사실 / 절차 |

**데이터 — 데이터셋 규모:**

| 항목 | 값 |
| --- | ---: |
| 골든셋 문항 | 80 |
| 리랭킹·문서길이 분석용 평가셋 | 300 |
| 대상 문서 | 850 |
| 청크 (500 tokens 기준) | 1,474 |

**시각화:**
- 좌측 60%: JSON 코드 블록 (구문 강조, `gold_doc_ids`와 `expected_evidence` 키를 강조색으로)
- 우측 40%: 규모 숫자 4개를 세로 스택 카드로

**발표 노트:**
- 평가 방식은 간단하다. 질문을 임베딩해서 각 전략의 청크와 코사인 유사도를 계산하고, 상위 k개 안에 정답 문서가 있으면 정답 처리한다
- 정답 판정은 **문서 단위**다. 정답 문서의 청크가 하나라도 들어오면 맞은 것으로 본다
- 지표는 Recall@3, Recall@5, MRR@5를 쓴다

## 슬라이드 3

> 내용이 많으면 3-A(overlap 양 변화) / 3-B(청크 크기·splitter 변화) 두 장으로 나눠도 된다.

**제목:** Overlap — RAG의 기본 관행이라 당연히 적용했다

**핵심 메시지:** overlap 양, 청크 크기, splitter 종류를 모두 바꿔가며 검증했으나 어느 조건에서도 개선이 없었다

**데이터 ①  — overlap 양을 바꿨을 때 (500 tokens 고정, 80문항):**

| 지표 | overlap 0 | overlap 50 | overlap 100 | overlap 150 |
| --- | ---: | ---: | ---: | ---: |
| 청크 수 | 1,474 | 1,503 | 1,531 | 1,581 |
| Recall@3 | 0.875 | 0.850 | 0.838 | 0.863 |
| Recall@5 | 0.912 | 0.950 | 0.900 | 0.938 |
| MRR@5 | 0.726 | 0.727 | 0.716 | 0.715 |

문항별 변화 (80문항):

| 비교 | 개선 | 악화 | 변화 없음 |
| --- | ---: | ---: | ---: |
| overlap 0 → 50 | 6 | 5 | 69 |
| overlap 0 → 100 | 3 | 5 | 72 |
| overlap 0 → 150 | 5 | 7 | 68 |

**데이터 ② — 청크 크기와 splitter를 바꿨을 때 (overlap = 청크 크기의 10%, 300문항):**

| 설정 | Recall@3<br>overlap 없음 | Recall@3<br>overlap 적용 | 차이 | Recall@5<br>overlap 없음 | Recall@5<br>overlap 적용 | 차이 | McNemar |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| **recursive 500** | 0.597 | 0.587 | −0.010 | 0.730 | 0.707 | −0.023 | p ≈ 0.900 |
| **fixed 300** | 0.617 | 0.610 | −0.007 | 0.710 | 0.700 | −0.010 | p ≈ 0.975 |
| **fixed 500** | 0.593 | 0.600 | +0.007 | 0.740 | 0.733 | −0.007 | p ≈ 0.973 |
| **fixed 1000** | 0.623 | 0.620 | −0.003 | 0.757 | 0.753 | −0.003 | p ≈ 1.000 |

→ **7개 비교 전부 p > 0.9. 어느 조건에서도 통계적으로 유의한 차이가 없다.**

**데이터 ③ — overlap이 실제로 적용된 비율 (반박 대비):**

| 설정 | overlap이 걸린 청크 경계 | 평균 이월 토큰 | 청크 수 증가 |
| --- | ---: | ---: | ---: |
| recursive 500 | **100.0%** | 41.8 | +2.3% |
| fixed 1000 | 86.1% | 78.4 | +0.5% |
| fixed 300 | 78.9% | 26.0 | +4.0% |

→ recursive는 **모든 경계에 overlap이 걸렸는데도** 개선이 없었다

**시각화:**
- 상단(3-A): Recall@5를 overlap 값에 따라 그린 **꺾은선 그래프** (x축 0/50/100/150)
  - 0.912 → 0.950 → 0.900 → 0.938로 **지그재그**임이 드러나야 한다. 이게 핵심
  - y축은 0.85~1.0 구간으로 좁혀 변동이 보이게 하되, "변동 폭이 작다"는 주석을 달 것
- 하단(3-B): 데이터 ②를 **양방향 막대(diverging bar)**로
  - 0을 중심선으로 두고 각 설정의 Recall@3 차이(−0.010 / −0.007 / +0.007 / −0.003)를 좌우 막대로
  - 막대가 전부 0 근처에 짧게 붙어 있는 모습이 결론 그 자체 — 축 범위를 −0.10 ~ +0.10으로 잡아 실제 변화가 얼마나 작은지 보이게 할 것
- 데이터 ③은 작은 보조 표로 우측 하단에

**발표 노트:**
- overlap은 청크 경계에서 정보가 끊기는 걸 막는 기법이다. RAG에서 거의 기본값으로 쓰인다
- 우리도 당연히 넣고 시작했고, 조작 변인은 overlap 하나로 통제했다
- 먼저 overlap 양을 바꿔봤다. Recall@5가 50에서 0.950으로 올랐다가 100에서 0.900으로 떨어지고 150에서 다시 0.938로 오른다. **실제 효과가 있으면 이런 지그재그가 나오지 않는다**
- "청크 크기 500에서만 본 것 아니냐"는 지적이 있을 수 있어 **범위를 넓혀 다시 검증했다**
- 청크 크기를 300 · 500 · 1000으로 바꾸고, splitter도 fixed-size 외에 recursive를 추가했다. **네 설정 모두 차이가 0.01 이하**였고 통계적으로 유의하지 않았다
- 혹시 overlap이 제대로 걸리지 않아 효과가 없었나 확인했더니, recursive에서는 **모든 경계에 100% 적용**됐는데도 결과가 같았다
- 즉 이건 특정 설정의 문제가 아니라 **우리 데이터의 성질** 때문이다. 다음 세 슬라이드에서 그 이유를 설명한다

## 슬라이드 4

**제목:** 사유 ① — 문서의 절반 이상이 500 토큰을 넘지 않는다

**핵심 메시지:** 애초에 잘리지 않는 문서가 58.4%라 overlap이 적용될 경계 자체가 없다

**데이터:**

| 문서당 청크 수 | 문서 수 | 비율 | 누적 |
| ---: | ---: | ---: | ---: |
| 1개 (분할 없음) | 496 | 58.4% | 58.4% |
| 2개 | 208 | 24.5% | 82.8% |
| 3개 | 79 | 9.3% | 92.1% |
| 4개 이상 | 67 | 7.9% | 100% |

**데이터 — 문서 길이:**

| 항목 | 값 |
| --- | ---: |
| 문서 길이 중앙값 | 445 토큰 |
| 청킹 기준 | 500 토큰 |

**시각화:**
- **도넛 차트 또는 가로 막대**: 1개 청크(58.4%)를 강조색으로, 나머지는 회색조
- 중앙 또는 옆에 큰 숫자 **58.4%** 배치
- 보조: "문서 길이 중앙값 445 토큰 < 청킹 기준 500 토큰"을 한 줄로

**발표 노트:**
- 우리 데이터는 학과 공지사항이라 대부분 짧다. 문서 길이 중앙값이 445 토큰으로 청킹 기준인 500 토큰보다 짧다
- 그래서 **문서의 58.4%는 애초에 나뉘지 않는다.** 청크가 하나뿐이면 이어붙일 앞 청크가 없으므로 overlap이 물리적으로 적용되지 않는다
- 82.8%가 청크 2개 이하다. 경계가 있어도 하나뿐이다
- overlap이 영향을 줄 수 있는 범위 자체가 좁았다

## 슬라이드 5

**제목:** 사유 ② — 문맥 보존이 중요한 데이터가 아니다

**핵심 메시지:** 공지사항은 소설처럼 문맥이 이어지지 않는다. 문단·리스트 단위로 내용이 독립적이다

**데이터 — 청크 경계 품질:**

| 항목 | 값 |
| --- | ---: |
| 이어지는 청크 경계 | 624개 |
| 문장 중간에서 끊긴 경계 | 68개 (10.9%) |
| **문장 단위로 온전한 경계** | **556개 (89.1%)** |

**데이터 — 분할 방식:**

| 단계 | 기준 |
| ---: | --- |
| 1 | 빈 줄 2개 → 문단 분리 |
| 2 | 리스트 마커(`-`, `1.`, `가.`) → 항목 분리 |
| 3 | 문장 종결 어미(`~다.`, `~요.`, `~니다.`) → 문장 분리 |
| 4 | 위 조각들을 500 토큰까지 이어붙임 |

**데이터 — 보조: 청킹 설계 특징 (작게 배치):**

모든 청크 앞에 제목 · 출처 · 분류 · 작성일을 붙인다. 문서가 나뉘어도 각 청크가 어느 문서의 것인지 스스로 갖고 있어 **출처 추적과 날짜 필터가 가능**하다. 전체 토큰의 14.1%를 차지한다.

```
제목: [수업] 2026-2학기 수강지도 상담 안내(7/27~8/5)   ← 헤더
출처: se게시판                                        ← 헤더
분류: 수업                                            ← 헤더
작성일: 2026-07-20                                    ← 헤더

수강지도 상담 양식은 https://... 에서 받을 수 있습니다.  ← 본문
```

**시각화:**
- 좌측: **큰 숫자 89.1%** + "청크 경계가 문장 단위로 온전"
- 우측: 분할 4단계를 **세로 플로우/스텝 다이어그램**으로
- 하단 보조: 문서 유형 대비를 아이콘 2개로 — "소설·논문(문맥 연속) ↔ 공지사항(문단 독립)"
- 헤더 예시는 우측 하단에 **작은 코드 블록**으로 (주된 메시지가 아니므로 작게)

**발표 노트:**
- overlap이 필요한 상황은 **문맥이 계속 이어지는 문서**다. 소설이나 논문처럼 앞 문단을 알아야 뒤 문단이 이해되는 경우다
- 우리 데이터는 공지사항이다. "신청 기간", "제출 서류", "유의사항"처럼 **문단마다 내용이 독립적**이다
- 그리고 우리 splitter는 문단 → 리스트 → 문장 순으로 **자연 경계에서만** 자른다. LLM이 아니라 규칙 기반 정규식이다
- 그 결과 청크 경계 624개 중 **89%가 문장 단위로 온전하게** 끊긴다. 문장 중간에서 잘리는 건 10.9%뿐이다
- 즉 overlap이 고쳐야 할 "끊긴 문맥"이 거의 발생하지 않았다
- (보조) 참고로 모든 청크에 헤더를 붙여 출처 추적이 가능하도록 했다

> **[발표자 주의] 헤더를 "overlap이 불필요한 이유"로 말하지 말 것.**
> 헤더를 제거한 대조군에서도 overlap 효과는 나타나지 않았다(R@3 0.620 → 0.613).
> 헤더는 출처 추적을 위한 **설계 선택**이지, overlap 무효의 원인이 아니다.
> 질문이 나오면: "헤더 유무와 무관하게 overlap 효과는 없었습니다. 헤더는 출처 표시와 날짜 필터를 위한 것입니다."

## 슬라이드 6

**제목:** 검증 — 문서가 길어지면 overlap은 실제로 효과가 나타난다

**핵심 메시지:** 같은 코퍼스 안에서도 문서가 1,000 토큰을 넘으면 overlap 효과의 부호가 뒤집힌다. 앞의 두 사유를 뒷받침하는 직접 증거다

**데이터 — 정답 문서 길이별 overlap(50) 효과 (300문항):**

| 정답 문서 길이 | 문항 수 | overlap 없음 | overlap 적용 | 차이 |
| --- | ---: | ---: | ---: | ---: |
| ~500 토큰 | 142 | 0.634 | 0.613 | −0.021 |
| 500 ~ 1,000 | 90 | 0.589 | 0.578 | −0.011 |
| **1,000 ~ 1,500** | 40 | 0.525 | 0.625 | **+0.100** |
| **1,500 이상** | 28 | 0.500 | 0.571 | **+0.071** |

*(Recall@3 기준)*

**데이터 — McNemar 검정 (승부가 갈린 문항만):**

| 구간 | overlap 없음 승 | overlap 적용 승 | p |
| --- | ---: | ---: | ---: |
| 짧은 문서 (< 1,000 토큰) | **7** | 3 | 0.638 |
| 긴 문서 (≥ 1,000 토큰) | 1 | **7** | 0.095 |

**데이터 — 그런데 우리 데이터에는 긴 문서가 적다:**

| 항목 | 값 |
| --- | ---: |
| 1,000 토큰 이상 문서를 다루는 질문 | 68 / 300 (22.7%) |

**시각화:**
- 메인: 문서 길이 구간을 x축으로, overlap 효과(차이)를 y축으로 한 **막대 그래프**
  - 0을 기준선으로, 짧은 구간 2개는 아래(음수·회색), 긴 구간 2개는 위(양수·강조색)
  - **부호가 뒤집히는 지점**이 시각적으로 명확히 보이는 것이 이 슬라이드의 전부
- 보조: 우측에 "1,000 토큰 이상 = 전체 질문의 22.7%"를 도넛 또는 큰 숫자로

**발표 노트:**
- 앞에서 "문서가 짧고 문맥 연속성이 낮아서 overlap이 무의미했다"고 설명했다. 그게 맞는지 **같은 데이터 안에서 확인해봤다**
- 질문을 정답 문서의 길이별로 나눠서 overlap 효과를 다시 계산했다
- 짧은 문서에서는 여전히 효과가 없거나 오히려 마이너스다. 그런데 **1,000 토큰을 넘어가면 +0.100, +0.071로 부호가 뒤집힌다**
- 승부가 갈린 문항만 보면 긴 문서에서는 **7 대 1로 overlap이 이긴다**. p=0.095로 통상적 유의수준 0.05에는 못 미치지만, 표본이 68문항뿐인 걸 감안하면 방향성은 분명하다
- 즉 **overlap이 쓸모없는 기법이 아니다. 유효 조건이 있고, 우리 데이터의 22.7%만 그 조건에 들어간다**
- 그래서 전체 평균으로는 상쇄되어 0이 된다

> **[발표자 주의]** p=0.095는 유의수준에 미달한다. "통계적으로 입증됐다"가 아니라
> **"같은 방향의 경향이 관찰됐다"**로 말할 것. 표본이 68문항이라는 점도 함께 언급.

## 슬라이드 7

**제목:** Overlap 결론 — 채택하지 않는다

**핵심 메시지:** 의미 있는 개선은 확인되지 않았고, 비용은 확인되었다

**데이터 — 개선 측:**

| 항목 | 결과 |
| --- | --- |
| Recall@3 / Recall@5 / MRR@5 | 일관된 개선 없음 (지그재그) |
| 80문항 중 변화 없는 문항 | 68~72문항 |
| McNemar 검정 (4개 비교) | 전부 p > 0.69 — 통계적 차이 없음 |

**데이터 — 비용 측:**

| 항목 | overlap 0 | overlap 적용 시 |
| --- | ---: | ---: |
| 청크 수 | 1,474 | 1,503 ~ 1,581 (+2 ~ 7%) |
| top-5 중복 낭비 슬롯 | 1.07개 | 1.18개 |
| top-5가 커버하는 서로 다른 문서 | 3.92개 | 3.83개 |

**시각화:**
- **좌우 대비 레이아웃**: 왼쪽 "개선 — 확인되지 않음"(회색), 오른쪽 "비용 — 확인됨"(적갈색)
- 하단에 결론 문장을 강조 박스로

**발표 노트:**
- 정리하면, 개선은 통계적으로 확인되지 않았고 비용은 명확히 발생한다
- 청크가 2~7% 늘어나 저장·임베딩 비용이 증가하고, 비슷한 청크가 검색 상위를 차지해 다른 문서가 밀려난다
- 그래서 **불필요한 복잡도를 제거하기로 했다**
- 다만 이 결론은 우리 데이터에 한정된다. 문단 구분 없이 길게 이어지는 산문이나 OCR 텍스트라면 결과가 달랐을 것이다
- 실제로 문서 길이가 1,000 토큰을 넘는 구간만 따로 보면 overlap이 유리해지는 경향이 나타났다. 다만 우리 데이터에서 그런 문서는 전체의 20% 남짓이라 전체 평균으로는 상쇄됐다

## 슬라이드 8

**제목:** 리랭킹 — 3개 모델을 300문항으로 비교했다 (현 설정 기준)

**핵심 메시지:** 코사인 검색 상위 50개를 후보로 두고 리랭커가 재정렬하도록 했다

**데이터 — 실험 설계:**

| 항목 | 내용 |
| --- | --- |
| 평가셋 | 300문항 |
| 후보군 | Chroma 코사인 검색 Top-50 |
| 기준선 | cosine (재정렬 없음) |
| 비교 모델 1 | `BAAI/bge-reranker-v2-m3` |
| 비교 모델 2 | `Qwen/Qwen3-Reranker-0.6B` |
| 실행 환경 | NVIDIA RTX 4070 SUPER |

**데이터 — 결과:**

| 전략 | Recall@3 | Recall@5 | MRR@5 | nDCG@5 | 평균 지연 |
| --- | ---: | ---: | ---: | ---: | ---: |
| cosine (기준선) | 0.5933 | **0.7400** | 0.5033 | 0.5619 | 0 ms |
| BGE | 0.5200 | 0.6900 | 0.4093 | 0.4788 | 1,736 ms |
| Qwen3 | **0.6300** | 0.7267 | 0.5092 | 0.5635 | 2,222 ms |

**시각화:**
- **그룹 막대 그래프**: x축에 지표(R@3, R@5, MRR@5, nDCG@5), 각 지표마다 3개 막대(cosine/BGE/Qwen3)
  - 막대 높이 차이가 크지 않다는 것이 그대로 보이게 (y축을 0부터 시작)
- 별도로 **지연 시간 막대**를 하나 더 (0 / 1,736 / 2,222 ms) — 여기서만 차이가 극적으로 보이게
- 슬라이드 하단에 **"현 설정 기준" 배지 또는 각주**를 반드시 표시

> **[발표자 주의] 리랭킹 결과는 overlap만큼 검증이 끝나지 않았다.**
> 아래 세 가지를 인지하고 말할 것.
>
> 1. 리랭커 입력 길이(`max_length`)를 지정하지 않아 **BGE 입력이 잘렸을 가능성**이 있다.
>    BGE의 저조한 성적은 모델 성능이 아니라 설정 문제일 수 있다.
> 2. `Qwen3-Reranker`는 causal LM 기반인데 `CrossEncoder`로 로드했다. 정식 사용법이 아닐 수 있다.
> 3. 300문항 실행 결과가 파일이 아닌 **화면 캡처로만 남아 있다.**
>
> → 따라서 "BGE가 나쁜 모델이다"라고 말하지 말고, **"현 설정에서는 이런 결과가 나왔다"**로 한정할 것.

**발표 노트:**
- 리랭킹은 검색으로 후보를 넓게 가져온 뒤 더 정교한 모델로 순위를 다시 매기는 기법이다
- 코사인 상위 50개를 후보로 두고, 두 개의 리랭커 모델로 재정렬했다
- 결과를 보면 **지표상 의미 있는 개선이 없다**. Qwen3가 Recall@3에서 0.5933 → 0.6300으로 조금 올랐지만 Recall@5는 오히려 0.7400 → 0.7267로 떨어졌다
- BGE는 모든 지표에서 기준선보다 낮았다
- 반면 지연 시간은 0ms에서 2.2초로 늘어난다. 검색 자체가 3ms인 것을 감안하면 500배 이상이다

## 슬라이드 9

**제목:** 리랭킹이 효과 없던 이유 — 문서 다양성 부족으로 추정된다

**핵심 메시지:** 학과 게시판 3년치 단일 도메인 데이터라 후보 문서들이 서로 비슷하다 — 검증된 인과가 아니라 정황에 기반한 해석이다

**데이터 — 데이터 출처 구성:**

| 출처 | 문서 수 | 비율 |
| --- | ---: | ---: |
| se게시판 (학과 공지) | 647 | 76.1% |
| 에브리타임 (강의평) | 196 | 23.1% |
| 학과공식사이트 | 7 | 0.8% |

**데이터 — 문서 유사성:**

| 항목 | 값 |
| --- | ---: |
| 연도·학기만 다른 반복 제목 문서 | 255개 (30.0%) |
| 동일 제목 패턴 최대 문서 수 | 20개 (`자료구조 (이현아) 강의평 1~20`) |

**데이터 — 검색 후보의 점수 밀집도 (300문항):**

| 항목 | 값 |
| --- | ---: |
| 1위와 5위의 유사도 차이 (중앙값) | 0.0449 |
| 1위와 10위의 유사도 차이 (중앙값) | 0.0775 |

**시각화:**
- 상단: 출처 구성을 **가로 스택 막대 1개**로 (se게시판이 76%를 차지하는 것이 보이게)
- 중앙: **점수 밀집도**를 시각화 — 예시 문항 1개의 top-5 유사도를 **점 플롯(dot plot)**으로 그려 5개 점이 좁은 구간에 몰려 있음을 보여줄 것
- 하단: 반복 제목 예시를 리스트로 (`자료구조 (이현아) 강의평 1`, `... 2`, `... 3` …)

**발표 노트:**
- 왜 리랭킹이 효과가 없었는지 생각해봤다
- 우리 데이터는 **학과 게시판 3년치를 수집한 것**이다. 출처가 3종뿐이고 그중 76%가 se게시판 하나다
- 즉 **하나의 도메인 안에 있는 비슷한 문서들**이다. 매년 반복되는 수강신청·장학금 공지처럼 연도·학기만 다른 문서가 30%나 된다. 강의평은 같은 제목을 가진 문서가 20개까지 있다
- 실제로 검색 결과를 보면 상위 5개의 유사도 차이가 중앙값 0.045에 불과하다. **55%의 문항에서 후보 5개가 0.05 이내로 몰려 있다**
- 리랭커는 "관련 있는 문서와 없는 문서"를 가려내는 데 강하다. 그런데 우리 후보군은 **전부 어느 정도 관련이 있는 비슷한 문서들**이라 리랭커가 판단할 근거가 부족했던 것으로 보인다
- 도메인이 다양한 데이터였다면 결과가 달랐을 수 있다

> **[발표자 주의] 이 슬라이드는 "해석"이지 "검증"이 아니다.**
> 출처 구성과 점수 밀집도는 실측값이지만, 그것이 리랭킹 무효의 **원인이라는 것은 증명하지 않았다.**
> 배제하지 못한 대안 설명이 남아 있다 — 리랭커 설정 문제(슬라이드 8 주의 참고), 한국어 처리 특성 등.
>
> → **"~때문이다"가 아니라 "~때문으로 보고 있다 / 추정한다"**로 말할 것.
> 질문이 나오면: "설정 문제 가능성을 아직 배제하지 못했습니다. 재검증이 필요한 부분입니다."

## 슬라이드 10

**제목:** 다음 단계 — 프롬프트 전략

**핵심 메시지:** 이전 대화는 "무엇을 찾을지"에만 쓰고, 사실의 근거로는 쓰지 않는다

**데이터 — 처리 흐름:**

| 단계 | 하는 일 | 입력 |
| ---: | --- | --- |
| 1 | 후속 질문을 독립형 검색 질의로 재작성 | 최근 대화 3쌍 + 현재 질문 |
| 2 | 검색 + 출처 분리 (공식 공지 / 학생 후기) | 독립형 질의 |
| 3 | 검색된 자료만으로 답변 생성 + 근거 번호 부착 | **현재 질문 + 검색 자료만** |

**데이터 — 동작 예시:**

| 사용자 대화 | 시스템 동작 |
| --- | --- |
| "수강지도 상담은 언제야?"<br>→ "그럼 승인 안 되면?" | 검색 질의: "2026-2학기 수강지도 상담 미승인 시 수강신청 제한" |
| "수강신청 알려줘"<br>→ "장학금도"<br>→ "그거 마감은?" | 대상이 둘이라 **되물음** (검색하지 않음) |

**시각화:**
- **가로 플로우 다이어그램**: 대화 이력 + 현재 질문 → 검색 계획기 → 검색 → 답변 생성
  - **검색 계획기에는 대화가 들어가지만, 답변 생성기에는 들어가지 않는 것**을 화살표로 명확히 구분
  - 이 분리가 이 슬라이드의 핵심이므로 시각적으로 가장 두드러지게
- 하단: 동작 예시 2개를 말풍선 형태로

**발표 노트:**
- 지금 챗봇은 질문 하나만 받는다. "그럼 승인 안 되면?" 같은 후속 질문을 처리하지 못한다
- 그래서 대화 맥락을 쓰되, **어디에 쓸지를 분리**하는 설계를 잡았다
- 검색 계획기는 대화를 읽어서 "무엇을 찾아야 하는지"를 정한다. 하지만 **답변 생성기는 현재 질문과 검색된 자료만 받는다**
- 이렇게 하면 이전 답변에 오류가 있어도 그게 다음 답변의 사실로 굳어지지 않는다
- 대상이 특정되지 않으면 추측해서 검색하지 않고 되묻는다

| --- | --- | --- |
| 청킹 | **fixed-size 500 tokens 유지** | 문서 길이 중앙값 445 토큰과 정합 |
| Overlap | **미채택** | 의미 있는 개선 없음 (McNemar p > 0.69), 청크 +2~7% |
| 리랭킹 | **현 단계 미채택** | 지표 개선 미미, 지연 +2.2초 |
| 프롬프트 전략 | **다음 단계 구현** | 설계 완료 |

**데이터 — 왜 효과가 없었는가 (요약):**

| 기법 | 검증 범위 | 효과가 없던 이유 | 근거 수준 |
| --- | --- | --- | --- |
| Overlap | overlap 4단계 × 청크 크기 3종 × splitter 2종 | ① 문서 58.4%가 단일 청크 ② 문맥 연속성이 중요하지 않은 공지 데이터 | **실측 + 내부 검증**<br>(긴 문서에서는 효과가 나타남) |
| 리랭킹 | 리랭커 2종 × 300문항 | 단일 도메인이라 후보 문서들이 서로 너무 비슷함 | **정황 기반 추정**<br>(설정 문제 미배제) |

**시각화:**
- 상단: 결정 표를 **판정 칩**과 함께 (유지=초록, 미채택=회색/적갈, 다음단계=강조색)
- 하단: "왜 효과가 없었는가" 요약을 **2열 카드**로

**발표 노트:**
- 두 기법 모두 일반적으로는 유효한 방법이다. 다만 **우리 데이터 특성에서는** 이득이 확인되지 않았다
- 중요한 건 "안 썼다"가 아니라 **"써보고 측정한 뒤 근거를 갖고 뺐다"**는 점이다
- 검증하지 않고 관행이라서 유지했다면 근거 없는 복잡도만 늘어났을 것이다
- 다음 발표까지는 프롬프트 전략을 구현해서 대화형 질의응답을 가능하게 만드는 것이 목표다

## 부록: 발표 중 예상 질문

| 질문 | 답변 |
| --- | --- |
| "overlap을 쓰면 성능이 나빠지나요?" | 아닙니다. **개선이 확인되지 않았을 뿐**이고, 통계적으로는 차이가 없습니다. 일부 지표에서는 오히려 미세하게 높았습니다. |
| "청킹을 LLM으로 했나요?" | 아닙니다. **100% 규칙 기반 정규식**입니다. 문단 → 리스트 마커 → 문장 종결 어미 순으로 자릅니다. |
| "500 토큰이 정확한 값인가요?" | tiktoken이 아니라 자체 추정 함수를 씁니다. 모든 실험에 동일 적용했으므로 **전략 간 비교는 유효**하지만 절대 토큰 수에는 오차가 있을 수 있습니다. |
| "리랭킹이 무조건 나쁜 건가요?" | 아닙니다. Qwen3는 Recall@3에서 기준선보다 높았습니다. **지연 2.2초 대비 이득이 부족**하다는 판단입니다. 데이터 도메인이 다양했다면 결과가 달랐을 수 있습니다. |
| "BGE 결과가 유독 나쁜 이유는?" | 리랭커 입력 길이 설정(`max_length`) 미지정으로 청크 뒷부분이 잘렸을 가능성이 있어 재검증이 필요합니다. **현 설정 기준** 결과로 봐주시면 됩니다. |
| "헤더를 붙였기 때문에 overlap이 필요 없던 것 아닌가요?" | 그 가설을 직접 검증했습니다. **헤더를 제거한 대조군에서도 overlap 효과는 없었습니다**(Recall@3 0.620 → 0.613). 헤더는 출처 추적과 날짜 필터를 위한 설계 선택이지 overlap 무효의 원인이 아닙니다. |
| "문서 특성 때문이라는 걸 어떻게 아나요?" | 같은 코퍼스 안에서 **문서 길이별로 나눠 재측정**했습니다. 1,000 토큰을 넘는 구간에서는 overlap 효과가 +0.100, +0.071로 부호가 뒤집혔습니다. 다만 표본이 68문항이라 p=0.095로, **경향이 관찰됐다**는 수준입니다. |
| "표본이 부족한 것 아닌가요?" | 80문항과 300문항 두 개 평가셋에서 모두 같은 방향의 결과가 나왔습니다. McNemar 검정으로 통계적 유의성도 확인했습니다. |
| "청크 크기 500에서만 본 것 아닌가요?" | 아닙니다. **청크 크기 300 · 500 · 1000**과 **splitter 2종(fixed-size · recursive)**을 조합해 총 4개 설정에서 검증했습니다. 7개 비교 전부 p > 0.9로 유의한 차이가 없었습니다. |
| "overlap이 제대로 적용은 된 건가요?" | 확인했습니다. recursive 500 설정에서는 **청크 경계의 100%에 overlap이 적용**됐고 평균 41.8토큰이 이월됐습니다. 그런데도 결과는 동일했습니다. |
