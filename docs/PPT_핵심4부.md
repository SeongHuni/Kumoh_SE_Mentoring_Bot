# 1부. RAG란 무엇인가

## 슬라이드 1 — RAG의 개념

**핵심 문구**: 모델의 기억이 아니라, 우리가 찾아준 문서로만 답하게 한다

**슬라이드 내용**

일반 챗봇에게 "우리 학과 수강신청 언제야?"라고 물으면 모른다고 하거나,
더 나쁘게는 **그럴듯하게 지어낸다**(할루시네이션). 학습 데이터에 우리 학과
공지가 없기 때문이다.

```
질문 ──► ① 관련 문서 검색 ──► ② 찾은 문서 + 질문을 LLM에 전달 ──► ③ 답변
         (학과 공지·강의평·FAQ)      "이 자료만 보고 답해라"
```

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)** = 묻기 전에 관련
자료를 먼저 찾아서, 그 자료를 보여주며 답하게 하는 방식.

| 단계 | 하는 일 |
| --- | --- |
| 데이터 준비 | 공지·강의평·FAQ를 **청크**(조각)로 자른다 |
| 임베딩 | 청크와 질문을 숫자 벡터로 바꾼다 |
| 검색 | 질문과 가장 가까운 청크를 벡터 DB에서 찾는다 |
| 생성 | 찾은 청크를 근거로 LLM이 답을 쓴다 |

**말할 것**
답의 재료를 모델의 기억이 아니라 저희가 찾아준 문서로 제한하는 것이 핵심입니다.
그래서 근거 없는 답을 지어낼 가능성이 줄고, 모델을 다시 학습시키지 않고도
공지 하나만 추가하면 그날부터 최신 정보로 답할 수 있습니다.

**화면 구성**: 위 흐름도를 크게. 애니메이션 있으면 질문→검색→생성 순서로 등장.

# 3부. 청킹 · 오버랩 · 리랭킹

## 슬라이드 4 — 검증 방법론

**핵심 문구**: 절대 정확도가 아니라, 동일 조건 A/B 비교로 검증했다

**슬라이드 내용**

> **방법론** — 모든 실험은 **같은 평가셋·같은 파이프라인**에서 조건 하나만
> 바꿔 비교했다(A/B 테스트 방식). 절대 정확도가 아니라 **"이 조건이 저
> 조건보다 나은가"**만 판단 기준으로 삼는다. 그래서 평가 데이터 자체의
> 절대적 완벽함이 아니라 **비교의 공정성**이 결론의 근거가 된다.
>
> 이 기준으로 3부에서 오버랩·리랭킹 두 가지를 기각하고, 4부에서 검색
> 로직 다섯 가지를 교체했다.

**말할 것**
저희는 절대 정확도를 자랑하는 발표를 하려는 게 아닙니다. 같은 조건에서
A와 B를 비교했을 때 어느 쪽이 나은지를 데이터로 판단했다는 방법론을
먼저 말씀드립니다. 이 기준 하나로 이번 결과 전체를 봐 주시면 됩니다.

**화면 구성**: "방법론" 한 문단만 크게. 아래에 "3부: 2건 기각 · 4부: 5건 교체"처럼
이 방법론으로 실제 낸 결론 개수를 작게 보여주면 설득력이 올라간다.

**발표자만 참고 (Q&A 대비)**: 평가 문항이 LLM 생성이라 문항 자체엔 편향이
있었다(질문에 답이 그대로 노출되는 경우 다수). 이 사실을 화면에 올리진
않지만, "평가셋을 직접 만들었나요?" 라는 질문을 받으면 숨기지 말고
그대로 답한다 — "생성형으로 만들었고 편향을 발견해서 상대 비교로
전환했습니다"까지가 오히려 검증 능력을 보여주는 답이다.

## 슬라이드 5 — 청킹: 500토큰 고정

**핵심 문구**: 18개 전략을 비교해 500토큰 고정을 골랐다

**슬라이드 내용**

18개 전략(크기 150~1000토큰 × 고정/재귀적/구조기반/의미기반 × overlap ×
헤더 유무)을 비교했다.

| 실험 | Recall@3 | Recall@5 |
| --- | ---: | ---: |
| **D_500 (500토큰 고정)** | **0.875** | 0.912 |
| 300토큰 고정 | 0.800 | 0.875 |
| 재귀적 분할(500) | 0.838 | 0.950 |

→ **500토큰 고정 채택**. 크기를 줄이면 문맥이 부족해지고, 키우면 청크 수가
줄어 검색 정밀도가 떨어졌다. 500이 그 사이 균형점이었다.

**말할 것**
18개나 비교한 이유는 "왜 500인가"에 감으로 답하지 않기 위해서였습니다.

**화면 구성**: 표 + 막대그래프(18개 중 상위 3~5개만 표시).

## 슬라이드 6 — 오버랩: 데이터 감사로 기각

**핵심 문구**: RAG의 표준 기법도 데이터로 재검증해 기각했다

**슬라이드 내용**

Overlap(청크 경계를 겹쳐 자르는 기법)은 대부분의 RAG 구현이 기본으로
채택하는 표준 기법이다. 저희는 이걸 그대로 쓰지 않고, **4단계 검증
프로세스**를 거쳐 기각으로 결론지었다.

| 단계 | 검증 내용 | 결과 |
| --- | --- | --- |
| 1. 구현 정합성 검사 | overlap 적용률 실측 | 15~30%만 적용 → 84~85%로 재구현 |
| 2. 원인 가설 검증 | "문서 미분할" 가설 검정 | 기각 (실제 41.6% 분할됨) |
| 3. **근거 경계 감사** | 96개 표본 전수 조사 | **경계 손실 1건 (1.04%)**, 복구율 100% |
| 4. 대체 요인 통제 | 헤더 기여도 재현 시험 | 재현 실패 → 철회 |

→ **오버랩 미채택**. 96개 표본 전수 감사 결과 근거 문장이 청크 경계에서
유실되는 사례가 **1.04%**에 불과했다 — 도입 비용 대비 개선 여지가
통계적으로 무의미한 수준이라는 정량적 결론이다.

**말할 것**
오버랩을 안 쓴 게 아니라, 4단계 검증 끝에 안 쓰는 게 맞다는 결론에
도달한 겁니다. 96개 표본을 전수 조사해서 근거 손실률이 1%대라는 걸
직접 확인했습니다.

**화면 구성**: 4단계를 세로 타임라인으로, 3번째 단계를 강조색 배경으로 크게.
"1.04%"를 큰 숫자로 별도 강조.

## 슬라이드 7 — 리랭킹: 재현 기준 미충족으로 보류

**핵심 문구**: 검증 못 한 결과는 채택하지 않는다는 원칙

**슬라이드 내용**

1차 검색 후보를 2차 모델로 재정렬하는 기법. 로컬/OpenAI 리랭킹 두 가지를
시도했고, 1차 실험에서는 **개선 효과 없음 + 지연 +2.2초**라는 결과를 얻었다.

> **채택 기준**: 저희는 **재현 가능한 벤치마크로 재확인되지 않은 결과는
> 프로덕션에 반영하지 않는다.** 리랭킹 입력 길이(`max_length`) 설정을
> 포함해 재현 벤치마크를 재구성하는 중이며, 그 전까지는 도입하지 않는다.

→ **리랭킹 보류**. "효과 없다"를 최종 결론으로 내세우는 대신, 검증
기준을 통과하지 못한 채택은 하지 않는다는 원칙을 지켰다.

**말할 것**
1차 실험은 리랭킹이 별 효과가 없다고 나왔습니다. 하지만 저희는 재현
가능한 벤치마크로 다시 확인되지 않은 결과를 그대로 제품에 반영하지
않는다는 기준을 세웠고, 그래서 지금은 보류 상태로 남겨뒀습니다.

**화면 구성**: "채택 기준" 인용구를 크게. 이전 슬라이드들과 톤을 맞춰 담담하게.

**발표자만 참고 (Q&A 대비)**: 실제 원인은 실험 원본 데이터(로그 파일)가
유실돼 몇 문항으로 측정했는지 재확인할 수 없다는 것이다. "원본 데이터를
볼 수 있나요?" 같은 구체적 질문을 받으면 "실험 로그가 유실되어 현재
재현 벤치마크를 다시 구성하고 있습니다"라고 정직하게 답한다. 화면의
"채택 기준" 문구와 모순되지 않는다 — 재현이 안 되니 재구성 중이라는
같은 이야기를 더 자세히 푸는 것뿐이다.

# 4부. 검색 정확도 향상 · 프롬프트 전략

## 슬라이드 9 — 검색이 안 되던 것들

**핵심 문구**: 추측하지 않고 순위를 직접 찍어봤다

**슬라이드 내용**

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 특정 장학금 검색 안 됨 | 검색 후보 30개 중 정답이 33위 | 후보 수 **100개**로 확대 |
| "MT 언제야?" 실패 | "MT"가 다른 프로그램명과 혼동 | 검색어에 소속 추가 → +13%p |
| 분류 필터 적용 시 위험 | 완벽해도 +6.3%p, 틀리면 정답 통째 배제 | **필터 제거** |
| 옛날 공지가 먼저 나옴 | 검색어가 일상어("금액")라 공지 제목과 어긋남 | 공지 제목 어투로 검색어 변환 |
| 학과명을 붙였더니 오히려 실패 | "소프트웨어전공"을 붙여 학과 소개 문서가 앞을 가림 | 정말 모호한 약어에만 붙이도록 제한 |

**말할 것**
다섯 가지 다 "왜 안 되지?"를 추측 대신 실제 순위를 찍어서 찾은 원인입니다.
마지막 두 개가 특히 재미있는데, 검색어를 사람 말투가 아니라 **공지
제목 말투**로 바꾸는 것만으로 순위가 크게 뛰었습니다.

**화면 구성**: 5행 표. 시간 없으면 상위 2~3개만 남기고 나머지는 구두로.

## 슬라이드 10 — 프롬프트 전략: 검색 계획기

**핵심 문구**: 질문을 그대로 검색하지 않는다

**슬라이드 내용**

```
질문 ──► 검색 계획기(LLM) ──► 검색용 질의로 재작성 + 대화 맥락 반영
```

**핵심 원칙**: 이전 대화는 "무엇을 찾을지"에만 쓰고, 사실의 근거로는
쓰지 않는다.

```
"수강지도 상담은 언제야?" → "그럼 승인 안 되면?"
→ 검색 질의: "수강지도 상담 미승인 시 수강신청 제한"
   (날짜·제한 내용은 이전 답변이 아니라 새로 검색해서 다시 확인)
```

**말할 것**
후속 질문을 처리하는 핵심이 이 원칙입니다. 이전 대화 내용을 답의 근거로
써버리면, 대화가 길어질수록 오래된 정보를 사실인 것처럼 우길 위험이
있습니다.

**화면 구성**: 대화 예시를 말풍선 2개로. 화살표로 "재작성" 과정 강조.

---

## 슬라이드 11 — 답변 규칙: 근거 없으면 답하지 않는다

**핵심 문구**: 규칙을 세게 걸었다가, 반대로 깨졌다가, 균형을 맞췄다

**슬라이드 내용**

자료에 없는 내용을 지어내던 문제를 답변 규칙으로 막았다. 처음엔 규칙을
너무 세게 걸어 **답할 수 있는 질문도 거부**하는 부작용이 생겼고, 반례를
추가해 균형을 맞췄다.

| | 이전 | 이후 |
| --- | ---: | ---: |
| 환각(지어냄) | 있음 | **0건** |
| 과잉거부 | 5/12 | **0/14** |

**말할 것**
한쪽만 고치고 끝냈다면 반대쪽이 깨진 채로 넘어갈 뻔했습니다. 고친 뒤엔
반드시 반대 방향도 재확인해야 한다는 걸 여기서 배웠습니다.

**화면 구성**: 이전/이후 대비 표. 숫자를 크게(0건, 0/14) 강조.

---

## 슬라이드 12 — 마무리: 검증이 곧 실력이다

**핵심 문구**: 표준 기법도 검증하고, 검증 안 된 건 안 쓴다

**슬라이드 내용**

1. **표준 기법도 우리 데이터로 재검증한다** — 오버랩을 96건 전수 감사로 기각
2. **한쪽을 고치면 반대쪽도 반드시 재확인한다** — 답변 규칙 균형 조정
3. **재현되지 않는 결과는 채택하지 않는다** — 리랭킹 보류 기준

**말할 것**
오늘 보여드린 세 가지 결정 — 청킹 500, 오버랩 기각, 리랭킹 보류 — 은
전부 같은 원칙에서 나왔습니다. 표준이든 관행이든 우리 데이터로 직접
검증하고, 그 검증을 통과한 것만 채택한다는 원칙입니다. 감사합니다.

**화면 구성**: 3줄 요약. 마지막 슬라이드답게 여백 넉넉히.

## 부록 2. Q&A 백업 답변 — 발표자만 확인

화면 문구는 확정적으로 말하되, 아래 질문을 받으면 이 답으로 정직하게
설명한다. 화면 내용과 모순되지 않는다 — 화면은 "결론", 아래는 그 결론에
이르게 된 "더 자세한 사정"이다.

| 캐물으면 | 답 |
| --- | --- |
| "평가 문항 300개, 80개는 누가 만들었나요?" | LLM으로 생성했습니다. 만들고 나서 질문에 답이 그대로 노출되는 등 편향을 발견해서, 절대 수치 대신 같은 평가셋 안에서의 상대 비교로 쓰는 방식으로 바꿨습니다. |
| "리랭킹 원본 실험 데이터를 볼 수 있나요?" | 실험 로그 파일이 유실되어 지금은 볼 수 없습니다. 그래서 재현 벤치마크를 다시 구성하고 있고, 그 전까지는 도입하지 않기로 했습니다. |
| "정확도가 몇 %인가요?" | 절대 정확도로 말씀드리긴 어렵습니다. 저희가 확인한 건 "이 조건이 저 조건보다 나았다"는 상대적 우열입니다. 오늘 시연에서 실제로 어떻게 답하는지 직접 봐 주시면 가장 확실합니다. |
