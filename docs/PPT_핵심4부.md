## 1. RAG란 무엇인가

일반 챗봇(GPT 등)에게 "우리 학과 수강신청 언제야?"라고 물으면 모른다고
하거나, 더 나쁘게는 **그럴듯하게 지어낸다**(할루시네이션). 학습 데이터에
우리 학과 공지가 없기 때문이다.

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)**는 "묻기 전에
관련 자료를 먼저 찾아서, 그 자료를 보여주며 답하게" 해서 이 문제를 푼다.

```
질문 ──► ① 관련 문서 검색 ──► ② 찾은 문서 + 질문을 LLM에 전달 ──► ③ 답변
         (학과 공지·강의평·FAQ)      "이 자료만 보고 답해라"
```

일반 챗봇과의 차이는 하나다. **답의 재료를 모델의 기억이 아니라 우리가
찾아준 문서로 제한한다.** 그래서 근거 없는 답을 지어낼 가능성이 줄고,
모델을 다시 학습시키지 않고도 공지 하나만 추가하면 그날부터 최신 정보로
답할 수 있다.

**이 프로젝트의 4단계**

| 단계 | 하는 일 |
| --- | --- |
| 데이터 준비 | 공지·강의평·FAQ를 **청크**(조각)로 자른다 |
| 임베딩 | 청크와 질문을 숫자 벡터로 바꾼다 |
| 검색 | 질문과 가장 가까운 청크를 벡터 DB에서 찾는다 |
| 생성 | 찾은 청크를 근거로 LLM이 답을 쓴다 |

## 3. 청킹 · 오버랩 · 리랭킹 — 시행착오와 최종 채택

### 청킹 — 500토큰 고정

18개 전략(크기 150~1000토큰 × 고정/재귀적/구조기반/의미기반 × overlap ×
헤더 유무)을 비교했다.

| 실험 | Recall@3 | Recall@5 |
| --- | ---: | ---: |
| **D_500 (500토큰 고정)** | **0.875** | 0.912 |
| 300토큰 고정 | 0.800 | 0.875 |
| 재귀적 분할(500) | 0.838 | 0.950 |

→ **500토큰 고정 채택.** 크기를 줄이면 문맥이 부족해지고, 키우면 청크
수가 줄어 검색 정밀도가 떨어졌다. 500이 그 사이 균형점이었다.

### 오버랩 — 사용 안 함

Overlap은 청크 경계를 겹치게 잘라 문맥 단절을 막는 RAG의 기본 기법이다.
**"우리는 필요 없다"는 결론에 여러 번의 재검증이 걸렸다** — 처음엔
구현 버그(적용률 15~30%)를, 다음엔 잘못된 설명("문서가 안 잘림", 실제론
41.6% 분할)을 반박했다.

**최종 근거**: 근거 문장이 청크 경계에 걸리는 경우를 96건 표본에서 직접
셌더니 **1건뿐**이었다(overlap은 그 1건을 100% 복구했다). 공지문은
소설과 달리 문단이 독립적이라, 애초에 overlap이 필요한 상황 자체가
드물었다.

→ **overlap 미사용 채택.** 효과가 없는 게 아니라, 효과가 나타날 상황이
우리 데이터엔 거의 없었다.

### 리랭킹 — 사용 안 함

1차 검색 후보를 2차 모델로 재정렬하는 기법. 로컬/OpenAI 리랭킹을 시도했고
**"현재 설정 기준으로는 안 쓰는 게 낫다"**(개선 미미, 지연 +2.2초)는
결론을 냈다.

다만 이 실험의 원본 데이터가 유실돼 몇 문항으로 측정했는지 확인할 수
없고, 리랭킹 모델의 입력 길이 설정이 잘못됐을 가능성도 재검증하지
못했다. **이 프로젝트에서 유일하게 결론이 완전히 확정되지 않은 항목**이다.

→ **리랭킹 미사용 채택** (단, "현재 설정 기준"이라는 단서가 붙는다).

## 4. 검색 정확도 향상 — 시행착오와 프롬프트 전략

배포 후 실제 질문으로 검증하며 "왜 안 되는지 추측하지 않고 순위를 직접
찍어보는" 방식으로 하나씩 고쳤다.

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 특정 장학금 검색 안 됨 | 검색 후보 30개 중 정답이 33위 | 후보 수 **100개**로 확대 |
| "MT 언제야?" 실패 | "MT"가 다른 프로그램명과 혼동 | 검색어에 소속 추가 → +13pp |
| 분류 필터 적용 시 위험 | 완벽해도 +6.3pp, 틀리면 정답 통째 배제 | **필터 제거** |
| 옛날 공지가 먼저 나옴 | 검색어가 일상어("금액")라 공지 제목과 어긋남 | 공지 제목 어투로 검색어 변환 |
| 학과명을 붙였더니 오히려 실패 | "소프트웨어전공"을 붙여 학과 소개 문서가 앞을 가림 | 정말 모호한 약어에만 붙이도록 제한 |

### 프롬프트 전략 — 검색 계획기(Query Planner)

질문을 그대로 검색하지 않고, LLM이 먼저 **"무엇을 어떻게 찾을지"** 계획을
세우도록 프롬프트를 설계했다.

```
질문 ──► 검색 계획기 ──► 검색용 질의 재작성 + 대화 맥락 반영
```

**핵심 원칙**: 이전 대화는 "무엇을 찾을지"에만 쓰고, 사실의 근거로는
쓰지 않는다. ("그럼 승인 안 되면?" → 새로 검색해서 확인하지, 이전 답변을
그대로 재사용하지 않는다.)

### 답변 규칙 — 근거 없으면 답하지 않는다

자료에 없는 내용을 지어내던 문제를 답변 규칙으로 막았다. 처음엔 규칙을
너무 세게 걸어 **답할 수 있는 질문도 거부**하는 부작용이 생겼고, 반례를
추가해 균형을 맞췄다.

| | 이전 | 이후 |
| --- | ---: | ---: |
| 환각(지어냄) | 있음 | **0건** |
| 과잉거부 | 5/12 | **0/14** |
