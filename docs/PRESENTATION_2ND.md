# 학과 챗봇 RAG — 2차 발표

**발표 순서**

1. 평가에 사용한 정답 데이터셋
2. Overlap을 적용했으나 성능이 개선되지 않은 이유
3. 리랭킹 전략별 성능 비교
4. 다음 단계 — 프롬프트 전략

---

## 0. 타이틀

**헤드라인:** 청킹 이후 — 무엇을 검증했고, 무엇을 채택하지 않았는가

**말할 내용:**
- 1차 발표: 10개 청킹 전략 비교 → `fixed-size 500 tokens` 채택
- 2차 발표 한 줄 요약: **"관행 두 가지를 시험했고, 둘 다 채택하지 않기로 했다 — 근거와 함께"**
  - Overlap: 검증했으나 유의한 개선 없음
  - 리랭킹: 검증했으나 지연 대비 이득 부족
- 채택하지 않은 것도 **측정하고 이유를 설명하면 결과**다

# 1부. 평가 데이터셋

## 1. 청킹 전략 비교에 사용한 정답 데이터셋

**헤드라인:** 질문 + 정답 문서 ID + 근거 + 채점 기준을 갖춘 골든셋으로 평가했다

> **[슬라이드에 골든셋 예시 이미지 삽입]**
> `outputs/golden_set/golden_questions.jsonl`의 실제 항목 1~2건 캡처

**말할 내용:**
- 경로: `outputs/golden_set/`
  - `golden_questions.jsonl` — 질문 80개
  - `sampling_manifest.json` — 카테고리별 샘플링 구성
  - `spot_check_sample.md` — 검수용 14문항

| 항목 | 값 |
| --- | --- |
| 총 문항 | 80 |
| 질문 유형 | 단일사실 75 / 절차 5 |
| 카테고리 | 수업 13, 행정·안내 11, 강의평 10, 학적·졸업 8, 장학금 8, 비교과·행사 8, 취업·진로 6, 연구·캡스톤 6, 학생회 5, 대학원 3, 기타 2 |

- 각 문항 구조 (이미지로 보여줄 부분)

```json
{
  "question": "2025-2학기 수강지도 상담 기간은 언제인가요?",
  "gold_doc_ids": ["kumoh-notice-44578"],
  "gold_category": "수업",
  "expected_evidence": ["2025-2학기 수강지도 상담 기간 : 7. 28.(월) 09:00 ~ ..."],
  "answer_checkpoints": ["상담 기간 시작일과 종료일", "상담 기간의 시간"],
  "question_type": "단일사실"
}
```

- **평가 방식**: 질문을 `text-embedding-3-small`로 임베딩 → 각 전략의 청크와 cosine 유사도 → `Recall@3/@5`, `MRR@5` 산출
- 정답 판정은 **문서 단위** — 정답 문서의 청크가 top-k에 하나라도 들어오면 정답
- 리랭킹 실험(3부)과 문서 길이 분석(2부 5장)은 별도로 구축한 **300문항 평가셋**(`outputs/human_made_data/`)을 사용했다

**→ 이 슬라이드는 짧게 넘어간다. 데이터셋 품질 이슈는 마지막 한계점에서 다룬다.**

**출처:** `outputs/golden_set/`

# 2부. Overlap 실험

## 2. Overlap은 RAG의 기본 관행이다 — 그래서 넣고 시작했다

**헤드라인:** 500 tokens 고정 후 overlap만 0 / 50 / 100 / 150으로 비교

**말할 내용:**
- 조작 변인은 **overlap 하나**. 분할 로직·청크 크기·임베딩 모델 전부 동일
- overlap의 이론적 근거: 청크 경계가 문장·문맥을 절단할 때 뒤 청크가 앞 내용을 이어받게 함

| overlap | 0 | 50 | 100 | 150 |
| --- | ---: | ---: | ---: | ---: |
| 청크 수 | 1,474 | 1,503 | 1,531 | 1,581 |
| Recall@3 | 0.875 | 0.850 | 0.838 | 0.863 |
| Recall@5 | 0.912 | **0.950** | 0.900 | 0.938 |
| MRR@5 | 0.726 | 0.727 | 0.716 | 0.715 |

- **Recall@5가 50 → 100 → 150에서 0.950 / 0.900 / 0.938 — 비단조**
  → 실제 효과가 있다면 나올 수 없는 패턴

- 문항별로 보면 대부분 아무 변화가 없었다

| 비교 | 개선 | 악화 | 무변화 | 순변화 |
| --- | ---: | ---: | ---: | ---: |
| ov0 → ov50 | 6 | 5 | 69 | +1 |
| ov0 → ov100 | 3 | 5 | 72 | −2 |
| ov0 → ov150 | 5 | 7 | 68 | −2 |

**출처:** `outputs/eval_results/retrieval_leaderboard.json` (80문항 골든셋)

## 3. [핵심] overlap은 정상 작동했다 — 고칠 문제가 없었을 뿐이다

**헤드라인:** 절단된 근거 96건 중 1건, overlap은 그 1건을 복구했다 (복구율 100%)

**말할 내용:**

**논리 4단계**

1. **공지사항은 문단·리스트·문장 종결이 뚜렷하다** — 소설처럼 문맥이 이어지는 산문이 아님

2. **그래서 규칙 기반 splitter가 자연 경계에서만 자를 수 있었다**
   - `splitNatural()`은 정규식 3단계: 빈 줄 2개(문단) → 리스트 마커 → 문장 종결 어미
   - 그 조각들을 500토큰까지 탐욕적으로 이어붙임
   - **청크 경계 624개 중 문장 중간 절단은 68개(10.9%)뿐**
   - **LLM이 아니라 100% 규칙 기반 정규식이다** (질문 나올 수 있음)

3. **정답 근거가 실제로 절단된 사례는 96건 중 1건**
   - 골든셋 `expected_evidence` 96건이 청크 안에 온전히 남는지 직접 측정
   - 못 찾은 19건 중 18건은 무분할 원문에도 없었음(골든셋 생성 시 재진술된 것)
   - **진짜 청킹으로 잘린 것은 1건**

4. **overlap은 그 1건을 복구했다**

| 실험 | 근거 문장 온전 보존 |
| --- | ---: |
| overlap 0 | 77/96 (80.2%) |
| overlap 50 / 100 / 150 | 78/96 (81.3%) |

→ overlap을 50에서 150으로 3배 늘려도 **추가 복구 0건**

**동시에 비용은 실재한다**
- 청크 수 +2.0% ~ +7.3%
- 근사 중복 청크가 top-5 잠식: 낭비 슬롯 1.07 → 1.18개, top-5가 커버하는 서로 다른 문서 3.92 → 3.83개

**출처:** `scripts/analyze-overlap.js`

## 4. 애초에 문서의 58%는 잘리지도 않는다

**헤드라인:** 문서 중앙값 445토큰 — 500토큰 기준에서 절반 이상이 단일 청크

**말할 내용:**

| 문서당 청크 수 | 문서 수 | 비율 | 누적 |
| ---: | ---: | ---: | ---: |
| 1개 | 496 | **58.4%** | 58.4% |
| 2개 | 208 | 24.5% | 82.8% |
| 3개 | 79 | 9.3% | 92.1% |
| 4개 이상 | 67 | 7.9% | 100% |

- 문서 길이 중앙값 **445토큰** — 500토큰 임계값보다 짧다
- **58.4%는 분할 자체가 없으므로 overlap이 물리적으로 적용 불가**
- 82.8%가 2개 이하 → 경계가 있어도 1개뿐

**주의 — 이렇게 말하면 안 됨:**
- ~~"2번째 청크가 50~100토큰으로 짧아서"~~ → **사실이 아님**
- 실제 2번째 청크 본문 중앙값은 **361토큰**(2개 청크 문서 기준 264토큰), 100토큰 미만은 10.5%뿐
- 이유: splitter가 첫 청크를 500까지 꽉 채우지 않고 문단 단위로 끊기 때문. 1번째 청크도 중앙값 327토큰으로 **양쪽이 고르게 나뉜다**

**출처:** `outputs/chunking_experiments/D_500/stats.json`

## 5. [핵심] overlap의 유효 조건을 찾았다 — 문서 길이

**헤드라인:** 문서가 1,000토큰을 넘으면 overlap 효과의 부호가 뒤집힌다

**말할 내용:**
- 300문항 평가셋을 **정답 문서 길이별로 나눠** overlap(50) 효과 측정

| 정답 문서 길이 | 문항 | ov0 R@3 | ov50 R@3 | 차이 |
| --- | ---: | ---: | ---: | ---: |
| ~500 토큰 | 142 | 0.634 | 0.613 | **−0.021** |
| 500~1,000 | 90 | 0.589 | 0.578 | −0.011 |
| 1,000~1,500 | 40 | 0.525 | 0.625 | **+0.100** |
| 1,500 이상 | 28 | 0.500 | 0.571 | **+0.071** |

- McNemar 검정(불일치 문항만 비교)

| 구간 | ov0만 성공 | ov50만 성공 | p |
| --- | ---: | ---: | ---: |
| 짧은 문서 (<1,000) | **7** | 3 | 0.638 |
| 긴 문서 (≥1,000) | 1 | **7** | 0.095 |

- 긴 문서에서는 **7:1로 overlap 우세**. p=0.095로 유의수준 0.05엔 못 미치지만 표본이 68문항뿐임을 감안하면 방향성은 분명
- **그런데 1,000토큰 이상 문서를 다루는 질문은 300개 중 68개(22.7%)뿐**
  → 전체 평균으로는 상쇄되어 순효과가 0

**한 줄 결론:**
> overlap의 이득 구간은 실재한다. 다만 우리 코퍼스의 22.7%만 그 구간에 있어 전체적으로는 상쇄된다.

**출처:** `outputs/eval_results/header_vs_overlap_raw.jsonl` (300문항 평가셋)

## 6. Overlap 결론

**헤드라인:** 개선은 확인되지 않았고, 비용은 확인되었다 — 그래서 채택하지 않는다

**말할 내용:**
- 300문항 평가셋 McNemar 검정: **4개 비교 모두 p > 0.69** = 통계적으로 차이 없음
- 비용: 청크 +2~7%, top-5 슬롯 중복 잠식

**표현 주의 (절대 이렇게 말하지 말 것):**
- ~~"overlap을 쓰면 성능이 나빠진다"~~ → 데이터가 지지하지 않음
  - 300문항에서는 overlap 50이 오히려 R@3 0.600 vs 0.593으로 근소 우위
  - 80문항 골든셋에서는 R@3는 낮지만 R@5는 0.950 vs 0.912로 높음
- **정확한 표현: "개선이 확인되지 않았고 비용은 확인되었다"**

**일반화 주의:**
- 이 결론은 **이 데이터셋과 이 splitter에 한정**
- 문단 구분 없는 산문, OCR 텍스트, 평균 1,000토큰 이상 문서라면 결과가 달라질 수 있음

# 3부. 리랭킹 전략 비교

## 7. 실험 설계

**헤드라인:** cosine Top-50을 후보로, 3개 리랭커가 재정렬

**말할 내용:**
- 평가셋: 300문항 (`outputs/human_made_data/`)
- 공통 검색: 500-token 청크 → `text-embedding-3-small` → Chroma cosine **Top-50**을 후보군으로
- 비교 전략

| 전략 | 방식 |
| --- | --- |
| cosine (기준선) | Chroma cosine 순위 그대로 |
| BGE | `BAAI/bge-reranker-v2-m3`로 Top-50 재정렬 |
| Qwen3 | `Qwen/Qwen3-Reranker-0.6B`로 Top-50 재정렬 |
| OpenAI listwise | LLM 기반 재정렬 — **190/300에서 크레딧 소진으로 중단** |

- 지표: Recall / MRR / nDCG @3, @5, @10
- 정답 판정: 문서 단위 (같은 문서의 여러 청크는 한 번만)
- 실행 환경: NVIDIA RTX 4070 SUPER, PyTorch 2.11.0+cu128

---

## 8. 리랭킹 결과 (300문항)

**헤드라인:** BGE는 명확히 악화, Qwen3는 top-3만 소폭 개선, cosine은 top-5에서 최고

| 전략 | R@3 | R@5 | R@10 | MRR@3 | MRR@5 | nDCG@3 | nDCG@5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **cosine** | 0.5933 | **0.7400** | 0.8367 | 0.4694 | 0.5033 | 0.5012 | 0.5619 |
| **BGE** | 0.5200 | 0.6900 | 0.8367 | 0.3700 | 0.4093 | 0.4084 | 0.4788 |
| **Qwen3** | **0.6300** | 0.7267 | 0.8367 | **0.4872** | **0.5092** | **0.5238** | **0.5635** |

**말할 내용:**
- **BGE**: 모든 지표에서 악화. R@3 −7.3pp(22문항), MRR@5 −9.4pp
- **Qwen3**: top-3 개선(R@3 +3.7pp = 11문항, nDCG@3 +2.3pp). 대신 R@5는 −1.3pp
- **지연 비용이 결정적**

| 전략 | 평균 리랭킹 시간 |
| --- | ---: |
| cosine | 0 ms |
| BGE | 1,736 ms |
| Qwen3 | 2,222 ms |

→ 검색 자체는 **3ms**. 리랭킹은 **500배 이상**의 지연을 추가한다

**출처:** `sw-rag-share/reRankingResult.png`, `sw-rag-share/outputs/cosine-baseline-300.md`

## 9. 리랭킹 결론

**헤드라인:** 지연 500배를 지불할 만한 이득이 없다 — 현 단계에서는 채택하지 않는다

**말할 내용:**
- 최종 사용자에게 노출되는 건 보통 top-3~5. 그 구간에서 Qwen3의 이득은 **R@3 +3.7pp(11문항)**뿐이고 R@5는 오히려 −1.3pp
- 그 대가로 응답에 **2.2초**가 추가된다
- BGE는 이득 없이 악화만 발생

**표현 주의:**
- ~~"리랭킹은 성능을 떨어뜨린다"~~ → Qwen3는 R@3·MRR·nDCG에서 cosine보다 높음
- **정확한 표현: "지연 대비 이득이 부족해 현 단계에서 채택하지 않는다"**

# 4부. 다음 단계 — 프롬프트 전략

## 10. 프롬프트 전략의 핵심 원칙

**헤드라인:** 이전 대화는 "무엇을 찾을지"에만 쓰고, 사실의 근거로는 쓰지 않는다

**말할 내용:**
- 현재 `ask.js`는 단일 질문만 받아 Top-k 검색 → 후속 질문("그럼 승인 안 되면?")을 처리 못 함
- 설계 3단계
  1. 짧은 후속 질문을 이전 대화와 합쳐 **독립형 검색 질의**로 재작성
  2. 그 질의로 Chroma 검색, **공식 공지와 학생 후기를 분리**
  3. 최종 답변은 검색된 자료만 사용, 모든 사실에 자료 번호 부착

- **핵심 분리**: 검색 계획기는 대화를 읽지만, **답변 생성기는 `현재 질문 + 검색 자료`만 받는다**
  → 이전 답변의 오류가 다음 답변의 사실로 전파되지 않음

**예시**

| 대화 | 검색 계획기 출력 | 답변 근거 |
| --- | --- | --- |
| "수강지도 상담 언제야?" → "그럼 승인 안 되면?" | `standalone_query`: "2026-2학기 수강지도 상담 미승인 시 수강신청 제한" | 해당 공지 원문 청크 |
| "수강신청 알려줘" → "장학금도" → "그거 마감은?" | `action`: **clarify** | 검색하지 않고 되물음 |

**출처:** `docs/PROMPT_STRATEGY.md`

## 11. 데이터 특성에 맞춘 설계 결정

**헤드라인:** 공식 공지와 학생 후기를 섞지 않는다

| 데이터 특성 | 설계 결정 | 이유 |
| --- | --- | --- |
| se게시판 1,253청크 / 학과공식사이트 19청크 | 일정·신청·학적·장학금은 `official_notice`만 검색 | 공식 안내와 후기의 권위를 섞지 않기 위해 |
| 에브리타임 강의평 202청크 | 후기 질문은 `student_review` 전용 | 주관적 의견을 규정처럼 답하지 않기 위해 |
| 날짜 없는 청크 27개 | "최근/마감"은 날짜 있는 자료만 사용 | 오래된 공지를 현재 정보로 말하지 않기 위해 |
| 한 문서가 여러 청크 | `original_id`로 중복 제거 | 같은 공지가 여러 출처처럼 보이지 않게 |
| 후기 202개는 URL 없음 | 링크는 metadata에서만 렌더링 | 링크 환각 방지 |

**말할 내용:**
- 프롬프트가 아니라 **애플리케이션 코드가 강제**하는 gate가 별도로 존재
  - `action=clarify/reject`이면 검색·생성 모델을 호출하지 않음 (fail-closed)
  - 관련성 임계값 미달 또는 문서 상충 시 `insufficient`/`conflict` 반환
  - 제목·게시일·URL은 모델이 생성하지 않고 metadata에서 렌더링

## 12. 프롬프트 전략 — 구현 상태 구분

**헤드라인:** 이것은 검증된 설계이며, 아직 구현 전이다

**말할 내용:**

  - LangChain history-aware retriever — 대화 이력 + 최신 질문 → 독립형 질문 재구성

## 14. 한계점 (질문 대비)

**헤드라인:** 이번 실험에서 확정하지 못한 것들

**말할 내용:**

**평가셋 관련 (가장 중요)**
- 두 평가셋(80문항 골든셋, 300문항 평가셋) **모두 사람이 직접 작성했다는 근거가 없다.** 둘 다 자동 생성된 것으로 보인다
- 두 셋의 성격이 다르다

| 지표 | 80문항 골든셋 | 300문항 평가셋 |
| --- | ---: | ---: |
| 질문–정답문서 제목 어휘 중복 | 32.6% | 18.2% |
| `expected_evidence` 원문 일치율 | 81.3% | 2.9% |
| 10개 전략 중 하나라도 top-5 성공 | 98.8% | 89.3% |

- **평가셋을 바꾸면 전략 순위가 재현되지 않는다.** 80문항 기준 검색 1위였던 `H_recursive_500`이 300문항 기준으로는 8위
  - 단, 극단 비교(500 계열 vs 150·300 계열)는 두 셋 모두에서 유의 → **"너무 잘게 쪼개면 나쁘다"는 결론은 유지**
  - 상위권 전략 간 차이는 300문항 기준 유의하지 않음 (D_500 vs A_document p=0.988)
- **따라서 개별 전략의 순위를 단정하면 안 된다.** `D_500` 채택은 "최고라서"가 아니라 "상위권 중 비용 효율이 좋아서"다

**기타**
- 토큰 카운팅이 tiktoken이 아닌 자체 추정 함수(`estimated_local_no_tiktoken`) → 상대 비교는 유효, 절대 토큰 수엔 오차 가능
- overlap 결론은 **검색 지표 기준** — 생성 품질에 대한 overlap 효과는 미측정
- overlap은 fixed-size 500에서만 검증 — 다른 청크 크기·splitter는 미검증
- 긴 문서 구간(≥1,000토큰) 표본이 68문항 — p=0.095는 유의수준 미달
- 리랭킹: `rerank-local.py`가 `CrossEncoder`에 `max_length`를 지정하지 않아 BGE 입력이 잘렸을 가능성 → BGE 악화의 원인일 수 있음
- 리랭킹: 세 전략의 Recall@10이 0.8367로 완전히 동일 — 집계 로직 확인 필요
- 리랭킹: OpenAI listwise는 190/300 중단으로 비교 불가
- 리랭킹 300문항 결과가 파일이 아닌 스크린샷으로만 존재 — 재실행하여 보존 필요
