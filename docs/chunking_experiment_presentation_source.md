# 학과 챗봇 RAG — 청킹 전략 비교 실험 발표 소스

---

## 0. 타이틀 슬라이드

**헤드라인:** 학과 챗봇 RAG, 어떤 청킹 전략이 가장 좋은가?

**말할 내용:**
- 부제: 리랭킹 없이 순수 청킹 전략만 비교한 정량 실험
- 10개 전략 × 80문항 골든셋 × 자동 평가(검색 4지표 + LLM-judge 5항목)
- 한 줄 결론: "검색 1위와 생성 품질 1위는 서로 다른 전략이었다"

---

## 1. 문제 정의

**헤드라인:** 청킹 방식에 따라 답변 품질이 달라지는데, 지금까지는 사람이 눈으로만 판단했다

**말할 내용:**
- 학과 챗봇 데이터 수집·정제는 완료된 상태
- RAG 파이프라인에서 검색 품질을 좌우하는 첫 단추가 청킹(Chunking) 전략
- 문제: 청킹 전략별로 답변을 사람이 매번 읽고 비교하는 방식은 스케일이 안 됨
- 목표: **자동화된 수치 비교**로 전환 + fixed-size 외 다른 전략(Recursive/Document-Specific/Semantic)까지 확장

---

## 2. 실험 설계 원칙

**헤드라인:** 청킹만 변수로 통제하고, 나머지는 전부 고정했다

**말할 내용:**
- 리랭커(cross-encoder/LLM) 사용 **안 함**
- 하이브리드(BM25+벡터) 검색 **안 함**
- 쿼리 재작성/확장/HyDE **안 함**
- 임베딩 모델 `text-embedding-3-small` 전 실험 고정
- 답변 생성 모델 `gpt-4o-mini`, temperature=0, 프롬프트 템플릿 전 실험 동일
- top-k=5 고정 (Recall@3은 top-5 결과 중 상위 3개로 별도 계산)

→ **이렇게 해야 "답변이 달라진 이유는 오직 청킹 방식 때문"이라고 말할 수 있음**

---

## 3. 데이터셋 스냅샷

**헤드라인:** 850개 문서, 짧은 강의평부터 6,800자 장문 공지까지 편차가 큼

**말할 내용:**
- 총 문서 850개
- 출처: `se게시판`(공지) 647개, `에브리타임`(강의평) 196개, `학과공식사이트` 7개
- 카테고리 11종: 강의평196 > 행정·안내123 > 수업116 > 비교과·행사110 > 학생회69 > 학적·졸업65 > 취업·진로51 > 연구·캡스톤50 > 장학금47 > 대학원13 > 기타10

## 4. 평가 방법론 — 두 축으로 나눠서 측정

**헤드라인:** "정답 자료를 찾았는가"(검색)와 "그 자료로 좋은 답을 만들었는가"(생성)를 분리해서 측정했다

**말할 내용 — 검색 지표 4종:**
| 지표 | 의미 |
|---|---|
| Recall@3 | top-3 안에 정답 문서가 있으면 1 |
| Recall@5 | top-5 안에 정답 문서가 있으면 1 |
| MRR@5 | 정답이 몇 번째 순위에 나왔는지의 역수 (1위=1.0, 5위=0.2, 못 찾으면 0) |
| Context Precision@5 | top-5 중 실제 정답 문서 청크의 비율 (노이즈 없는 정도) |

**말할 내용 — 생성 지표: LLM-judge 5항목 (0~2점)**
- 정확도 / 근거충실도(환각 체크) / 세부정보보존(날짜·기간·문의처 등) / 출처제시 / 완성도
- 골든셋 80문항: 카테고리 가중 샘플링, 원문(A_document) 기준 생성, 질문+참고답변+체크리스트 자동 생성

## 6. Fixed-size 그룹 (A~F) — 개념

**헤드라인:** 가장 단순한 baseline — 토큰 수로 기계적으로 자름

**말할 내용:**
- 문단→리스트→문장 순으로 자연 경계를 최대한 지키려 하되, 결국 목표 토큰 수를 넘으면 무조건 자름
- 이 데이터는 **본문에 실제 줄바꿈이 거의 없어서**(850개 중 476개가 본문 내부 줄바꿈 0), 사실상 "문장 단위로 쪼개서 목표 크기까지 채우기"에 가깝게 동작함
- 크기가 작을수록(B_150) 세부 문장 검색엔 유리하지만 절차 정보가 여러 조각으로 흩어짐
- 크기가 클수록(E_800, F_1000) 문맥은 보존되지만 여러 주제가 한 청크에 섞여 검색 정밀도 저하

---

## 7. Recursive Character Splitting (G, H) — 메커니즘

**헤드라인:** 같은 목표 크기라도 "어디서 자르는지"가 검색 성능을 좌우한다

**말할 내용 — 동작 원리:**
1. 빈 줄(문단) 구분자가 있으면 그걸로 먼저 자름
2. 없으면 줄바꿈으로
3. 없으면 **인라인 리스트 마커**("1. ... 2. ...", "가. ... 나. ...")로 — 이 데이터에서 실제로 가장 많이 작동하는 tier
4. 없으면 문장 단위로
5. 그래도 넘치면 강제 토큰 분할

**말할 내용 — 가장 까다로웠던 기술적 문제:**
- "2026. 7. 9.(목)" 같은 날짜의 "7."을 리스트 항목 "7번"으로 착각하는 오탐 위험
- 해결: 숫자 마커는 문서 순서상 **실제로 증가하는 수열**(1→2→3...)을 이룰 때만 진짜 리스트로 인정 → 날짜 조각은 이 패턴을 안 만들어서 자동 배제
- 검증 결과: 850개 중 218개 문서에서 리스트 분할이 실제로 발동, 날짜 오탐 없음 확인

**말할 내용 — 결과:** `H_recursive_500`이 검색 성능 전체 1위 (Recall@5 0.950) — 같은 500토큰대인 fixed-size D_500(0.913)보다 우수. **크기가 같아도 자르는 위치가 문장/리스트 경계와 맞으면 검색이 더 잘 된다는 증거.**

---

## 8. Document-Specific Splitting (I) — 메커니즘

**헤드라인:** 문서 출처와 주제에 맞는 규칙을 직접 설계해서, 절차 정보가 흩어지지 않게 만들었다

**말할 내용 — 2단계 파이프라인:**

**1단계 (출처별 규칙, 잘게 쪼갠 조각 생성):**
- 에브리타임(강의평): 400토큰 이하면 통짜 유지 (median 222자라 대부분 여기 해당)
- se게시판(공지): "신청기간/신청대상/신청방법/제출서류/문의처/유의사항" 같은 행정 키워드를 우선 분할 기준으로 삼음
- 학과공식사이트: 600토큰 이하면 통짜 유지 (실제론 7개 문서 전부 이미 단일 주제라 이 규칙은 거의 항상 "그냥 유지"로 귀결)

**2단계 (카테고리별 병합, 관련 조각 다시 합치기):**
- 수업/학적·졸업/장학금 → "기간+대상+방법+서류+문의처"를 최대 900토큰까지 하나로 병합
- 비교과·행사/연구·캡스톤/취업·진로 → "모집대상+일정+링크+담당자" 병합
- 강의평 → 무조건 통짜 1개 (한 리뷰 = 하나의 판단 단위)

**말할 내용 — 왜 "1단계 다음에 2단계" 순서가 중요했는가 (실제로 겪은 시행착오):**
- 처음엔 1단계에서 이미 350토큰 단위로 다 packing까지 해버렸는데, 그러면 2단계 병합 로직이 "이미 여러 주제가 섞인 350토큰 블록"의 앞부분만 보고 병합 여부를 판단하게 되어 제대로 못 합쳤음
- **잘게 쪼갠 상태에서 먼저 병합하고, 최종 사이즈 패킹은 맨 마지막에** 하도록 순서를 바꾸자 청크 수가 1,819개 → 1,242개로 줄고, 절차 정보가 훨씬 깔끔하게 뭉침
- 이 교훈 자체가 발표에서 좋은 인사이트: **"규칙 기반 청킹은 순서 설계가 결과를 좌우한다"**

---

## 9. Semantic Chunking (J) — 메커니즘

**헤드라인:** 규칙을 직접 안 짜도, 임베딩 유사도만으로 비슷한 수준의 응집도를 만들어냈다

**말할 내용:**
1. 문서를 문장 단위로 분할 (850개 문서 → 약 9,073개 문장 단위)
2. 각 문장을 임베딩 (배치 임베딩 142회 호출)
3. 인접 문장 간 코사인 유사도 계산
4. 유사도가 "문서 내 평균 − 1×표준편차"보다 급격히 떨어지는 지점을 경계 후보로 표시
5. **강제 병합 규칙**으로 "신청기간+신청방법", "지원대상+제외대상", "일정+장소" 등 특정 키워드 쌍 사이의 경계는 취소
6. 120토큰 미만 청크는 인접과 병합, 900토큰 초과 청크는 재분할

**말할 내용:** 사람이 직접 규칙을 짜지 않았는데도, 같은 장학금 공지에서 I_docspec과 거의 동일한 결과(846+175토큰 2개 청크)에 도달함 — 통계적 방법만으로도 도메인 규칙과 비슷한 효과를 낼 수 있다는 증거.

## 12. [핵심 슬라이드] 왜 I_docspec이 생성 품질 1위인가

**헤드라인:** 검색 단계에서 이미 "필요한 정보를 한곳에 모아둔" 것이 답변 품질로 직결됐다

**말할 내용 — 인과관계 체인 (발표 핵심):**

1. **문제 상황**: 장학금/졸업 공지 같은 절차형 문서는 "신청기간 + 대상 + 방법 + 문의처"가 답변에 다 필요한데, 이게 서로 다른 청크에 흩어지면 LLM이 top-5 중 일부만 보고 답하게 되어 정보 누락 발생
2. **I_docspec의 해법**: 청킹 "생성" 단계에서 미리 이 필드들을 같은 청크로 병합해둠 (카테고리별 `mergeKeepTogether` 오버레이)
3. **검색 단계에서의 효과**: 정답 청크를 못 찾는 비율은 fixed-size보다 오히려 약간 높음 (Recall@5 0.875, 전체 4~6위) — 청크가 커서(중앙값 352, p90 854) 후보 자체가 fixed-size보다 적기 때문
4. **하지만 일단 찾으면**: 그 청크 안에 필요한 정보가 거의 다 들어있어서 LLM이 "여러 조각을 종합"할 필요 없이 "이미 완결된 문단을 요약"만 하면 됨
5. **결과적으로**: 정확도 1.86(1위), 세부정보보존 1.71(1위) — 정보가 흩어지지 않았기 때문에 날짜·기간·문의처 같은 세부사항을 놓치지 않음

**말할 내용 — 실제 증거 (같은 문서로 비교, kumoh-notice-49075 장학금 공지, 원문 967토큰):**

| 전략 | 청크 수 | 신청정보가 몇 조각에 흩어졌나 |
|---|---:|---|
| B_150 | 8개 | 신청자격/접수기간/입력방법/선발방법/장학금액이 전부 따로따로 |
| C_300 | 4개 | 여전히 분산 |
| D_500 | 2개 | 절반씩 분산 |
| **I_docspec** | **2개** | **신청자격+기간+방법+선발+금액 전부 청크 0(844토큰)에 뭉침, 청크 1(177토큰)은 부가 유의사항만** |

→ 같은 "2개 청크"라도 D_500은 기계적으로 절반씩 자른 것이고, I_docspec은 **의미 단위로 완결된 덩어리**로 나눈 것 — 이 차이가 생성 품질 점수 차이(D_500 composite 1.66 vs I_docspec 1.70)로 이어짐

**말할 내용 — 왜 근거충실도(환각 체크)는 거의 모든 전략에서 2.00으로 비슷한가:**
- `gpt-4o-mini`가 "제공된 자료로만 답하라"는 프롬프트 지시 자체는 잘 따름 → 이 지표는 전략 간 차이가 크게 안 드러남
- **차이는 정확도·세부정보보존에서 발생** → 즉 "환각을 안 하는 것"과 "필요한 정보를 다 담는 것"은 별개의 문제이고, 청킹 전략이 실제로 개선하는 건 후자

## 13. 검색 1위 ≠ 생성 1위, 무엇을 의미하는가

**헤드라인:** "검색이 잘 되는 것"과 "답변이 좋은 것"은 같지 않다

**말할 내용:**
- `H_recursive_500`(검색 1위, Recall@5 0.950)은 촘촘하게 잘라서(중앙값 386토큰) 검색 정밀도는 높지만, 하나의 절차가 2개 청크로 나뉘는 경우가 여전히 있어 top-5 안에 필요한 정보가 다 안 모일 수 있음
- `I_docspec`(생성 1위)은 검색 단계에서 약간 손해를 보더라도(Recall@5 0.875), 일단 찾은 청크 안에 정보가 완결돼 있어 생성 단계에서 유리
- **실무 시사점**: RAG 파이프라인에서 청킹 전략을 검색 지표만 보고 고르면 안 된다. 최종 사용자가 보는 건 답변이므로 검색·생성 두 지표를 함께 봐야 한다

## 14. 2차 실험 — 평가 데이터셋을 사람이 직접 만들었다

**헤드라인:** 1차의 골든셋은 LLM이 만들었다. 그래서 사람이 300문항을 직접 작성해 다시 검증했다

**말할 내용:**
- 1차 골든셋(80문항)은 `gpt-4o-mini`가 문서를 보고 생성 → **편향 가능성**
- 2차: 사람이 직접 작성한 **300문항** (`outputs/human_made_data/`)
  - `test_data.json` — 질문 300개
  - `answer_data.json` — 정답 문서 ID, 근거 문장(`expected_evidence`), 채점 기준(`answer_checkpoints`)
  - 두 파일을 `id`로 조인. 정답 문서 300개 전부 코퍼스에 존재함을 검증 완료
- 출처 분포: se게시판 252 / 에브리타임 41 / 학과공식사이트 7
- 카테고리 11종 (수업 46, 강의평 41, 학적·졸업 39, 행정·안내 37, 비교과·행사 30, 장학금 30, 취업·진로 23, 학생회 21, 연구·캡스톤 18, 기타 8, 대학원 7)
- **표본이 80 → 300으로 늘어 1문항의 무게가 1.25pp → 0.33pp로 감소** → 작은 차이를 판별할 수 있게 됨

**발견한 문제 (정직하게 언급할 것):**
- LLM 생성 골든셋은 **질문이 문서 제목을 되풀이하는 경향**이 있었다
  - 질문 단어 중 정답 문서 제목에도 등장하는 비율: LLM셋 **32.6%** vs 사람셋 **18.2%**
  - 50% 이상 겹치는 질문: LLM셋 21.3% vs 사람셋 4.7%
- 그 결과 LLM 골든셋 기준 성능이 부풀려져 있었음 (Recall@3 0.875 → 사람셋 0.593)
- LLM셋 `expected_evidence` 96건 중 **18건(18.8%)이 원문에 없는 문장** — 요약·재진술로 생성된 탓

## 15. Overlap 실험 — 우리도 당연히 넣고 시작했다

**헤드라인:** overlap은 RAG의 기본 관행이다. 그래서 4개 조건으로 실험했다

**말할 내용:**
- 500 tokens 고정 후 overlap만 `0 / 50 / 100 / 150`으로 변화
- 분할 로직·청크 크기·임베딩 모델 전부 동일. **조작 변인은 overlap 하나**

| overlap | 0 | 50 | 100 | 150 |
| --- | ---: | ---: | ---: | ---: |
| 청크 수 | 1,474 | 1,503 | 1,531 | 1,581 |
| Recall@3 | 0.875 | 0.850 | 0.838 | 0.863 |
| Recall@5 | 0.912 | 0.950 | 0.900 | 0.938 |
| MRR@5 | 0.726 | 0.727 | 0.716 | 0.715 |

- **Recall@5가 50 → 100 → 150에서 0.950 / 0.900 / 0.938로 비단조**
  → 실제 효과가 있다면 나올 수 없는 패턴. 노이즈 신호
- 문항별로 보면 대부분 아무 일도 일어나지 않았다

| 비교 | 개선 | 악화 | 무변화 | 순변화 |
| --- | ---: | ---: | ---: | ---: |
| ov0 → ov50 | 6 | 5 | 69 | +1 |
| ov0 → ov100 | 3 | 5 | 72 | −2 |
| ov0 → ov150 | 5 | 7 | 68 | −2 |

**중요 — 표현에 주의할 것:**
- "overlap을 쓰면 성능이 나빠진다"는 **말하면 안 된다.** 데이터가 지지하지 않는다
- 사람 300문항 + McNemar 검정에서 **4개 비교 모두 p > 0.69** = 통계적으로 차이 없음
- 정확한 표현: **"개선이 확인되지 않았고 비용은 확인되었다"**

## 16. [핵심 슬라이드] overlap이 효과 없던 이유를 규명했다

**헤드라인:** overlap은 정상 작동했다. 고칠 문제가 우리 데이터에 없었을 뿐이다

**말할 내용:**

**논리 4단계로 설명한다:**

1. **공지사항은 문단·리스트·문장 종결이 뚜렷하다**
   → 소설처럼 문맥이 이어지는 산문이 아님

2. **그래서 규칙 기반 splitter가 자연 경계에서만 자를 수 있었다**
   - `splitNatural()`은 정규식 3단계: 빈 줄 2개(문단) → 리스트 마커 → 문장 종결 어미
   - 그 조각들을 500토큰까지 탐욕적으로 이어붙임
   - **청크 경계 624개 중 문장 중간에서 끊긴 것은 68개(10.9%)뿐**

3. **결과: 정답 근거가 실제로 절단된 사례는 96건 중 1건**
   - 골든셋 `expected_evidence` 96건이 청크 안에 온전히 남는지 직접 측정
   - 못 찾은 19건 중 **18건은 원문(무분할 baseline)에도 없었음** = 골든셋 생성 문제
   - **진짜 청킹으로 잘린 것은 1건**

4. **overlap은 그 1건을 복구했다 — 복구율 100%**
   - 즉 기법은 제대로 작동했다. 대상이 없었을 뿐이다

**동시에 비용은 실재한다:**
- 청크 수 +2.0% ~ +7.3% (저장·임베딩·인덱스 비용)
- 근사 중복 청크가 top-5를 잠식: 중복 낭비 슬롯 1.07 → 1.18개, top-5가 커버하는 서로 다른 문서 3.92 → 3.83개

→ **효과 없음 + 비용 있음 = 제거가 합리적인 설계 결정**

**주의:** 이 결론은 **이 데이터셋과 이 splitter에 한정**된다. 문단 구분 없는 산문이나 OCR 텍스트라면 결과가 달라질 수 있다.

## 17. 애초에 우리 문서 절반 이상은 잘리지도 않는다

**헤드라인:** 500토큰 기준에서 문서의 58.4%는 단일 청크 — overlap이 개입할 경계 자체가 없다

**말할 내용:**
- 문서 850개 → 청크 1,474개
- 문서 길이 중앙값 **445토큰** — 500토큰 임계값보다 짧다

| 문서당 청크 수 | 문서 수 | 비율 | 누적 |
| ---: | ---: | ---: | ---: |
| 1개 | 496 | 58.4% | 58.4% |
| 2개 | 208 | 24.5% | 82.8% |
| 3개 | 79 | 9.3% | 92.1% |
| 4개 이상 | 67 | 7.9% | 100% |

- **58.4%는 분할 자체가 일어나지 않으므로 overlap이 물리적으로 적용 불가**
- 82.8%가 2개 이하 → 경계가 있어도 1개뿐
- 이것이 15·16번 슬라이드 결과의 **구조적 배경**

**연결 문장:** "500토큰이 우리 데이터에 잘 맞는 크기였다는 뜻이기도 하다. 문서 대부분이 한 청크에 담기면서도 긴 공지는 적절히 나뉜다."

## 18. 다음 단계 ① — 리랭킹 전략 비교 (진행 예정)

**헤드라인:** 검색은 후보를 넓게 가져오고, 순위는 리랭커가 정한다

**말할 내용:**
- 현재는 벡터 유사도 top-k를 **그대로** 답변 생성에 사용 (리랭킹 없음)
- 사람 300문항 기준 현재 성능: **Recall@1 0.373 / Recall@3 0.593 / Recall@5 0.740**
  → top-5 안에는 74% 들어오지만 **1위 정확도는 37%** = 순위 재조정 여지가 큼
- 비교 예정 전략:
  1. Cross-encoder 리랭커 (BGE-reranker 계열)
  2. LLM-as-reranker
  3. MMR (다양성 기반 재배치)
  4. RRF (BM25 + 벡터 융합)
  5. 메타데이터 부스팅 (최신성·출처 가중)
- **평가 지표는 동일하게 유지** — Recall@1/3/5, MRR@5, ContextPrecision@5
- 리랭킹이 유효할 것으로 보는 근거: 실험 중 `static-*` 문서군처럼 유사도가 0.544~0.573 구간에 촘촘히 몰려 순위가 불안정한 사례를 확인함

## 20. 한계점 (발표에서 질문 나올 만한 포인트 미리 대비)

**헤드라인:** 이번 실험에서 아직 다루지 않은 것들

**말할 내용:**
- 1차 골든셋 80문항 — 카테고리당 2~13문항 수준이라 세부 트렌드 확정엔 표본 부족 (→ 2차 300문항으로 보완)
- LLM-judge 1개 모델·1회 채점 — 채점자 편향/일관성 오차 가능성, 다수결 채점 미검증
- Semantic Chunking의 경계 임계값("평균−1×표준편차", 최소/최대 120/900토큰)은 이 데이터셋에 맞춘 경험적 값
- 학과공식사이트 7개뿐 — Document-Specific의 "섹션 분할" 규칙이 사실상 검증 안 됨
- 일부 일정표 텍스트에서 인라인 마커가 과분할되는 극소수 케이스 (그리디 패킹 단계에서 대부분 재병합되어 영향 제한적)
- **토큰 카운팅이 tiktoken이 아닌 자체 추정 함수** (`estimated_local_no_tiktoken`)
  → 모든 실험에 동일 적용했으므로 **전략 간 상대 비교는 유효**하나 절대 토큰 수엔 오차 가능
- **overlap 결론은 검색 지표 기준** — 생성 품질에 대한 overlap 효과는 아직 측정하지 않음
- overlap 실험은 fixed-size 500 기준으로만 수행 — 다른 청크 크기나 다른 splitter에서의 재현은 미검증
