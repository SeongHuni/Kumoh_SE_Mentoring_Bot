# 청킹 전략 비교 실험 결과 보고서

학과 챗봇 RAG 파이프라인을 위한 청킹(Chunking) 전략 10종을 구현하고, 골든 테스트셋 80문항 기반 자동 평가(검색 지표 + LLM-judge 생성 품질 평가)로 비교한 결과를 정리한다. 리랭킹, 하이브리드 검색, 쿼리 재작성 등 다른 최적화 기법은 일절 사용하지 않고, **오직 청킹 방식만을 변수로 통제**했다.

---

## 1. 핵심 요약

- **검색 성능 1위**: `H_recursive_500` (Recall@5 = 0.950, MRR@5 = 0.724) — Recursive Character Splitting을 목표 500토큰으로 적용한 버전. 같은 크기의 fixed-size(`D_500`, Recall@5 0.913)보다도 우수.
- **생성 품질 1위**: `I_docspec` (종합 1.70/2.00, 근거충실도 2.00/2.00) — 출처/카테고리 규칙 기반 Document-Specific Splitting. 절차형 정보(신청기간+대상+방법+문의처)를 한 청크에 묶어둔 효과.
- **검색 1위와 생성 1위가 서로 다른 실험**이라는 점이 이번 실험의 가장 중요한 발견이다 — "검색이 잘 되는 것"과 "실제 답변 품질이 좋은 것"은 동일하지 않다.
- **최하위권**: 청킹을 아예 하지 않은 `A_document`(baseline)와 지나치게 잘게 자른 `B_150`이 검색·생성 양쪽에서 모두 하위권 — 사전 예상과 일치.
- **300~500토큰 구간**이 이 데이터셋에서 전반적으로 가장 안정적인 목표 크기였다.

---

## 2. 프로젝트 배경 및 목적

학과 챗봇의 데이터 수집·정제가 끝난 상태에서, RAG 파이프라인의 검색 품질을 좌우하는 첫 단계인 **청킹 전략**을 정량적으로 선정하기 위해 이 실험을 진행했다. 목표는 다음과 같다.

- fixed-size 청킹뿐 아니라 Recursive / Document-Specific / Semantic 청킹까지 총 10개 실험을 동일한 조건에서 비교
- 사람이 매번 답변을 읽고 판단하는 방식은 스케일이 안 되므로, 골든 테스트셋 기반 자동 평가(검색 지표 + LLM-judge)로 전환
- 리랭커, 하이브리드(BM25+벡터) 검색, 쿼리 재작성/확장 등 **다른 최적화 기법은 배제**하여 청킹 자체의 순수한 효과만 분리해서 관찰

### 통제 변수 (모든 실험 동일)

| 항목 | 값 |
|---|---|
| 임베딩 모델 | `text-embedding-3-small` |
| 답변 생성 모델 | `gpt-4o-mini`, temperature=0 |
| 검색 방식 | 순수 코사인 유사도 top-k (리랭킹 없음) |
| top-k | 5 (Recall@3은 top-5 중 상위 3개로 별도 계산) |
| 프롬프트 템플릿 | 전 실험 동일 |

## 4. 평가 방법론

### 골든 테스트셋

- 총 **80문항**, `A_document`(원문 그대로) 기준으로 샘플링 — fixed-size 등 특정 실험의 청크 경계에서 뽑으면 그 실험에 유리하게 편향되므로 항상 원문에서 질문 생성
- 카테고리 가중 샘플링 (계획 문서의 목표 비율을 80문항 규모로 스케일): 수업 13, 행정·안내 11, 강의평 10, 학적·졸업 8, 장학금 8, 비교과·행사 8, 취업·진로 6, 연구·캡스톤 6, 학생회 5, 대학원 3, 기타 2
- 카테고리 내에서는 토큰 길이 상위 60% 풀에서 가중 샘플링 (긴 절차형 문서에서 전략 차이가 더 잘 드러나므로), 짧은 문서도 배제하지 않음
- 문항당 LLM 1회 호출로 질문·참고답변·근거·체크포인트 생성 (질문 유형: 단일사실/절차/조건/비교/최신성/링크요구)
- 생성 후 무작위 14문항(~18%)을 사람이 스팟체크

### 검색 지표

| 지표 | 정의 |
|---|---|
| Recall@3 | top-3 안에 정답 문서(`gold_doc_ids`)와 일치하는 청크가 있으면 1 |
| Recall@5 | top-5 안에 정답 문서와 일치하는 청크가 있으면 1 |
| MRR@5 | 첫 정답 청크가 나온 순위의 역수 (top-5 밖이면 0) |
| Context Precision@5 | top-5 중 실제 정답 문서 출처 청크의 비율 |

### 생성 품질 지표 (LLM-judge, 0~2점 루브릭)

정확도 / 근거충실도 / 세부정보보존 / 출처제시 / 완성도 — 5개 항목을 0(틀리거나 근거 없음)~2(정확하고 근거 충분)점으로 채점. "근거충실도"가 환각(hallucination) 여부를, "정확도"가 정답(reference_answer) 대비 사실 정합성을 담당한다.

## 5. 청킹 전략별 상세

### 5.1 Fixed-size 청킹 (A~F, 6종)

문서를 목표 토큰 수 단위로 기계적으로 자르는 baseline 그룹. `A`는 청킹을 아예 하지 않은 원문(baseline), `B~F`는 150/300/500/800/1000토큰을 목표로 자연 경계(문단→리스트→문장) 우선 분할 후 그리디 패킹.

| 실험 | 목표 토큰 | 청크 수 | 토큰 median | p90 | max | 문서당 청크 median (max) |
|---|---:|---:|---:|---:|---:|---:|
| A_document | 없음(원문) | 850 | 445 | 1,183 | 4,988 | 1 (1) |
| B_150 | 150 | 4,206 | 170 | 205 | 229 | 4 (41) |
| C_300 | 300 | 2,184 | 286 | 350 | 373 | 2 (21) |
| D_500 | 500 | 1,474 | 379 | 541 | 568 | 1 (13) |
| E_800 | 800 | 1,100 | 427 | 820 | 872 | 1 (8) |
| F_1000 | 1000 | 996 | 445 | 982 | 1,068 | 1 (6) |

**예시 — 장학금 공지(`kumoh-notice-49075`, 원문 967토큰) 분할 비교:**

- `B_150` → 8개 청크 (189/166/140/169/185/141/184/171 토큰): "신청자격"과 "제출점수 입력방법"이 서로 다른 청크로 완전히 분리됨
- `C_300` → 4개 청크 (349/338/349/93 토큰)
- `D_500` → 2개 청크 (502/519 토큰)
- `F_1000` → 1개 청크 (967 토큰, 원문과 동일 — 애초에 목표 크기보다 짧아서 분할 안 됨)

### 5.2 Recursive Character Splitting (G, H)

`scripts/create-chunks-recursive.js`. 단순 토큰 수 자르기 대신, **구분자 우선순위 tier**를 재귀적으로 시도해 자연스러운 경계를 최대한 지킨다.

```
tier 1: 빈 줄(문단 구분)
tier 2: 단일 줄바꿈
tier 3: 인라인 리스트 마커 ("1. ... 2. ...", "가. ... 나. ...")
tier 4: 문장 구분 (마침표/물음표/느낌표, "-다./-요./-니다." 등)
fallback: 토큰 수 기준 강제 분할
```

이전 tier의 구분자가 텍스트에 없으면 자동으로 다음 tier로 내려간다. 이 데이터는 **본문 내 실제 줄바꿈이 거의 없어서**(850개 중 476개는 본문 내부 줄바꿈 0), tier 1~2는 대부분 발동하지 않고 tier 3(인라인 리스트 마커)이 핵심 역할을 한다.

인라인 리스트 마커 검출이 까다로운 이유는 **날짜 표기와의 오탐 위험** 때문이다. "2026. 7. 9.(목)"의 "7."을 리스트 항목으로 착각하면 안 된다. 이를 위해:
- 숫자 마커는 문서 순서상 실제로 증가하는 수열(1, 2, 3...)을 이룰 때만 인정 (날짜 조각은 이 패턴을 만들지 않음)
- "다"처럼 리스트 문자(가나다라...)이면서 동시에 "-습니다" 같은 문장 종결어미로도 매우 흔히 쓰이는 글자는, 공백/문장 시작 뒤에 단독 토큰으로 등장할 때만 마커로 인정 (그렇지 않으면 "바랍니다." 같은 평범한 문장이 리스트 항목으로 잘못 잘림)
- 검증 결과 850개 문서 중 218개에서 인라인 마커 분할이 실제로 발동했고, 날짜 오탐은 발생하지 않음을 확인

목표 크기는 계획 문서의 1차 후보(300/500토큰)를 그대로 사용해 두 버전을 생성했다.

| 실험 | 목표 토큰 | 청크 수 | 토큰 median | p90 | max |
|---|---:|---:|---:|---:|---:|
| G_recursive_300 | 300 | 2,134 | 286 | 350 | 373 |
| H_recursive_500 | 500 | 1,448 | 386 | 539 | 568 |

**예시 — 같은 장학금 공지, `H_recursive_500`:** 2개 청크(491 / 530 토큰)로 자연스럽게 나뉘며, `D_500`(502/519, 순수 토큰 컷)과 청크 수는 같지만 경계 위치가 문장/리스트 항목 단위와 더 잘 맞아떨어진다 — 이 미세한 차이가 검색 지표에서 fixed-size보다 나은 결과로 이어졌다.

### 5.3 Document-Specific Splitting (I)

`scripts/create-chunks-docspec.js` → `I_docspec` (규칙 기반이라 크기 축이 없어 실험 1개). 출처별 규칙을 먼저 적용한 뒤, 카테고리별 규칙으로 한 번 더 병합(merge) 오버레이를 씌운다.

**출처별 규칙:**
- `에브리타임`(강의평): 기본 통짜 유지(median 222자로 매우 짧음), 400토큰 초과 시에만 문단/문장 단위로 분할 (인라인 리스트 마커 tier는 건너뜀 — 리뷰 속 우연한 숫자 오탐 방지)
- `se게시판`: "신청기간/신청대상/신청방법/제출서류/문의처/유의사항" 등 행정 키워드를 인라인 마커보다 먼저 시도하는 tier를 추가해 300~400토큰 목표로 분할
- `학과공식사이트`: 600토큰 이하면 통짜 유지. (실제 7개 문서를 확인해보니 이미 각각 단일 주제라 애초에 섹션 제목 기반 분할이 발동할 케이스가 없었음 — 계획 단계에서는 "섹션별 분할"을 예상했으나 실제 데이터에는 해당 안 됨)

**카테고리별 병합 오버레이:**
- 강의평 → 무조건 통짜 1개 (한 리뷰 = 하나의 판단 단위)
- 수업/학적·졸업/장학금 → "기간+대상+방법+서류+문의처" 그룹을 최대 900토큰까지 병합
- 비교과·행사/연구·캡스톤/취업·진로 → "모집대상+일정+링크+담당자" 그룹을 최대 900토큰까지 병합
- 학생회/행정·안내/기타 → 오버레이 없음

| 실험 | 청크 수 | 토큰 median | p90 | max | 강의평 청크 수 |
|---|---:|---:|---:|---:|---:|
| I_docspec | 1,242 | 352 | 854 | 1,176 | 196 (에브리타임 196개 문서와 1:1 일치) |

**예시 — 같은 장학금 공지, `I_docspec`:** "신청자격+제출기간+제출방법+선발방법+장학금액"이 전부 **하나의 844토큰 청크**로 병합되고, 뒤쪽 "기타 유의사항"만 별도 177토큰 청크로 분리됨. fixed-size/recursive가 만드는 2~8개 조각과 달리, 신청에 필요한 핵심 절차 정보가 끊기지 않는다 — 이것이 생성 품질 1위의 핵심 이유로 보인다.

### 5.4 Semantic Chunking (J)

`scripts/create-chunks-semantic.js` → `J_semantic`. 고정 길이가 아니라 **내용 전환 지점**을 찾아 자르는 방식.

```
1. 문서를 문장/짧은 문단 단위로 분할 (850개 문서 → 약 9,073개 단위)
2. 각 단위를 text-embedding-3-small로 임베딩 (배치 임베딩, 총 142회 API 호출)
3. 인접 단위 간 코사인 유사도 계산
4. 유사도가 "문서 내 평균 - 1×표준편차"보다 낮아지는 지점을 경계 후보로 표시
5. 강제 병합 오버라이드: 아래 키워드 쌍 사이의 경계는 취소
   (신청기간+신청방법, 지원대상+제외대상, 제출서류+제출처, 일정+장소,
    과목명+교수명+강의평본문, 문의처+담당부서)
6. 결과 청크가 120토큰 미만이면 인접 청크와 병합
7. 900토큰 초과 시 Recursive 방식으로 재분할 (목표 300~600토큰)
```

문장 단위 임베딩이 추가로 필요해 준비 비용이 다른 전략보다 크지만(1회성 비용, 평가 단계에는 영향 없음), 순수 통계 기반 경계 탐지에 도메인 특화 병합 규칙을 얹어 완전 자동임에도 Document-Specific과 비슷한 수준의 응집도를 만들어냈다.

| 실험 | 청크 수 | 토큰 median | p90 | max |
|---|---:|---:|---:|---:|
| J_semantic | 1,437 | 325 | 625 | 940 |

**예시 — 같은 장학금 공지, `J_semantic`:** `I_docspec`과 거의 동일하게 846토큰 + 175토큰의 2개 청크로 수렴 — 규칙을 직접 짜지 않고도 유사도 기반 경계 탐지 + 강제 병합 오버라이드만으로 사실상 같은 결과에 도달했다는 점이 인상적이다.

## 6. 비교분석

### 6.1 검색 성능 비교 (Recall@5 내림차순)

| 실험 | Recall@3 | Recall@5 | MRR@5 | Context Precision@5 | 청크 수 | 평균 latency(ms) |
|---|---:|---:|---:|---:|---:|---:|
| H_recursive_500 | 0.838 | **0.950** | 0.724 | 0.290 | 1,448 | 3.49 |
| D_500 | 0.875 | 0.913 | **0.726** | 0.293 | 1,474 | 3.30 |
| F_1000 | 0.775 | 0.900 | 0.650 | 0.220 | 996 | 3.19 |
| C_300 | 0.800 | 0.875 | 0.648 | 0.358 | 2,184 | 4.70 |
| I_docspec | 0.775 | 0.875 | 0.675 | 0.262 | 1,242 | 3.11 |
| J_semantic | 0.788 | 0.875 | 0.646 | 0.275 | 1,437 | 3.30 |
| B_150 | 0.775 | 0.863 | 0.700 | **0.467** | 4,206 | 10.08 |
| E_800 | 0.775 | 0.863 | 0.659 | 0.233 | 1,100 | 2.40 |
| G_recursive_300 | 0.788 | 0.863 | 0.628 | 0.333 | 2,134 | 6.11 |
| A_document | 0.725 | 0.838 | 0.612 | 0.167 | 850 | 3.13 |

**해석:**
- **300~500토큰 구간이 최적 지대**: C/D/G/H가 모두 상위권에 몰려 있고, 그보다 작거나(B_150) 크면(E_800, F_1000, A_document) 성능이 떨어지는 경향이 뚜렷하다. 계획 문서의 사전 예상("C와 D가 1차 후보")과 정확히 일치한다.
- **같은 크기라도 자르는 방식이 검색 성능을 좌우한다**: `H_recursive_500`(Recall@5 0.950)이 같은 500토큰대인 `D_500`(0.913)보다 우수하고, `G_recursive_300`(0.863)도 순수 토큰 컷인 `C_300`(0.875)과 대등하거나 약간 낮다 — 500토큰대에서는 자연 경계 보존이 뚜렷한 이득으로 나타났다.
- **Context Precision과 Recall은 반비례 경향**: `B_150`은 Context Precision@5가 0.467로 압도적 1위지만(청크가 잘게 쪼개져 있어 top-5 안에 같은 문서 청크가 여러 개 들어가기 쉬움), Recall@5는 0.863으로 중하위권 — "정밀하지만 놓치는" 전형적인 소형 청크의 트레이드오프.
- **latency**: 모든 실험이 10ms 이내로 실무상 무시 가능한 수준이나, `B_150`(청크 수 4,206개, 10.08ms)이 가장 느리고 `E_800`(1,100개, 2.40ms)이 가장 빠름 — 청크 수와 대략 비례.

### 6.2 생성 품질 비교 (composite 내림차순)

| 실험 | 정확도 | 근거충실도 | 세부정보보존 | 출처제시 | 완성도 | composite |
|---|---:|---:|---:|---:|---:|---:|
| I_docspec | **1.86** | 2.00 | **1.71** | 1.01 | 1.90 | **1.70** |
| E_800 | 1.85 | 2.00 | 1.66 | 1.03 | **1.91** | 1.69 |
| F_1000 | 1.85 | 1.99 | 1.68 | 0.99 | 1.90 | 1.68 |
| J_semantic | 1.85 | 1.98 | 1.68 | 1.00 | 1.89 | 1.68 |
| D_500 | 1.81 | 2.00 | 1.64 | 1.00 | 1.88 | 1.66 |
| H_recursive_500 | 1.80 | 2.00 | 1.61 | 1.00 | 1.85 | 1.65 |
| C_300 | 1.76 | 1.95 | 1.57 | 1.03 | 1.84 | 1.63 |
| A_document | 1.74 | 1.96 | 1.55 | 1.01 | 1.83 | 1.62 |
| G_recursive_300 | 1.73 | 1.93 | 1.56 | 1.00 | 1.81 | 1.61 |
| B_150 | 1.69 | 1.96 | 1.45 | 1.01 | 1.73 | 1.57 |

**해석:**
- **콘텐츠 응집도가 생성 품질을 좌우한다**: `I_docspec`이 5개 항목 중 정확도·세부정보보존에서 1위를 차지한 이유는, 청킹 단계에서 "신청기간+대상+방법+문의처"를 이미 한 청크로 묶어뒀기 때문에 LLM이 답변 시 여러 청크를 종합할 필요 없이 근거가 한곳에 모여 있었기 때문으로 보인다.
- **너무 잘게 쪼갤수록 세부정보보존이 떨어진다**: `B_150`이 세부정보보존 1.45로 전체 최하위 — 날짜/기간/문의처 같은 정보가 여러 청크로 흩어지면서 top-5 검색으로도 필요한 조각을 다 못 모으는 경우가 발생한 것으로 추정된다.
- **출처제시는 전 실험이 대체로 낮고 비슷함(0.99~1.03)**: 이는 청킹 전략과 무관하게 프롬프트가 "출처 번호를 표시하라"고만 지시했을 뿐 실제 URL/제목을 명시하도록 강하게 요구하지 않았기 때문으로, 청킹의 영향이 아니라 프롬프트 설계의 한계로 보인다.
- **근거충실도(환각 체크)는 대부분 실험에서 1.9 이상으로 높음**: `gpt-4o-mini` 자체가 "제공된 자료로만 답하라"는 지시를 비교적 잘 따랐다는 뜻이며, 이 지표만으로는 전략 간 차이가 크게 드러나지 않았다 — 차이는 주로 정확도·세부정보보존에서 발생했다.

### 6.3 검색 1위와 생성 1위가 다른 이유

`H_recursive_500`(검색 1위)와 `I_docspec`(생성 1위)의 차이는, **"정답이 담긴 청크를 찾아내는 능력"**과 **"찾은 청크로 완전한 답을 만드는 능력"**이 서로 다른 최적화 지점을 가진다는 것을 보여준다. `H_recursive_500`은 청크 경계가 촘촘해서(중앙값 386토큰) 검색 정밀도는 높지만, 하나의 절차 공지가 2개 청크로 나뉘는 경우가 여전히 있어 top-5 안에 필요한 정보가 다 모이지 않을 수 있다. 반면 `I_docspec`은 검색 단계에서 살짝 손해를 보더라도(Recall@5 0.875) 일단 정답 청크를 찾으면 그 안에 필요한 정보가 거의 다 들어있어 생성 단계에서 유리하다.

**실무 시사점:** RAG 파이프라인을 설계할 때 "검색 지표만으로 청킹 전략을 고르면 안 된다" — 최종 사용자가 보는 것은 답변이므로, 검색·생성 두 지표를 함께 봐야 한다.

### 6.4 한계점

- **골든셋 규모(80문항)**: 카테고리당 2~13문항 수준이라 카테고리별 세부 트렌드(예: "장학금 카테고리에서만 어떤 전략이 특히 강한가")를 통계적으로 확정하기엔 표본이 적다.
- **LLM-judge 자체의 신뢰도**: 채점자도 `gpt-4o-mini` 1개 모델 1회 채점이라, 채점자 편향이나 일관성 오차가 그대로 결과에 반영될 수 있다. 여러 judge의 다수결이나 사람 채점과의 교차검증은 하지 않았다.
- **Semantic Chunking의 임계값은 휴리스틱**: "평균 - 1×표준편차"라는 경계 기준과 최소/최대 토큰(120/900) 값은 이 데이터셋에 맞춰 경험적으로 정한 값으로, 다른 데이터셋에 그대로 적용 가능하다고 보장할 수 없다.
- **학과공식사이트 표본 부족(7개)**: Document-Specific 전략의 "섹션 단위 분할" 규칙이 이 소스에서는 사실상 검증되지 못했다 (7개 문서 모두 이미 단일 주제였음).
- **일부 일정표 형태 텍스트에서 과분할**: 인라인 리스트 마커 검출이 "9:00 ~ 7. 23.(목)" 같은 일정 표 안의 숫자를 리스트 항목으로 오인하는 극소수 케이스가 있었으나(그리디 패킹 단계에서 대부분 재병합되어 실질적 영향은 제한적).
- **Context Precision@5는 절대값으로 해석 주의**: 정답 문서가 보통 1개뿐이라 이론적 최댓값이 1/5=0.2에 가까운데, 청크가 여러 개로 나뉜 문서(B_150 등)는 top-5 안에 같은 문서의 청크가 여러 개 들어갈 수 있어 이 값이 구조적으로 더 높게 나온다 — 전략 간 상대 비교에만 사용해야 한다.

## 7. 결론 및 권장사항

**최종 후보:** 검색·생성 지표를 종합했을 때 `I_docspec`(생성 1위, 검색 상위권)과 `H_recursive_500`(검색 1위, 생성 상위권)이 가장 유력한 후보다. 규칙 유지보수 비용을 감수할 수 있다면 `I_docspec`을, 범용성과 낮은 유지보수 비용을 우선한다면 `H_recursive_500`을 권장한다.

**다음 단계 제안 (대화 중 논의된 아이디어 포함):**
1. `docs/chunking_strategy_plan.md`의 2차 실험(Overlap)을 `H_recursive_500` 또는 `D_500` 기준으로 진행 — 지금은 overlap=0으로 고정되어 있어 청크 경계에서 정보가 끊기는 경우를 아직 다루지 않았다.
2. 문서 길이에 따라 목표 청크 크기 자체를 가변적으로 조정하는 전략 (대화 중 제안된 아이디어) — 지금 10개 전략 모두 "문서가 짧으면 안 자름"까지는 이미 하지만, 목표 크기 자체가 문서 길이에 비례해 달라지는 방식은 아직 시도하지 않았다.
3. 골든셋을 60~100문항 이상으로 확장하고, judge를 다수결(예: 3개 모델/3회 채점) 구조로 바꿔 신뢰도를 높이는 방안.
4. `I_docspec`과 `H_recursive_500`을 결합한 하이브리드 전략(예: se게시판은 규칙 기반, 그 외는 recursive) 실험.
