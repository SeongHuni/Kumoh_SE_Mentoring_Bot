## 1차 실험: Chunk 크기만 비교

1차 실험은 overlap 없이 chunk size만 바꿔서 비교한다. 목적은 이 데이터셋에서 너무 작은 chunk와 너무 큰 chunk가 검색 품질에 어떤 차이를 만드는지 확인하는 것이다.

| 실험 | Chunk 크기 | 의미 |
| --- | ---: | --- |
| A | 문서 1개 | Chunking 안 함 (Baseline) |
| B | 150 tokens | 매우 작은 Chunk |
| C | 300 tokens | 작은 Chunk |
| D | 500 tokens | 중간 Chunk |
| E | 800 tokens | 큰 Chunk |
| F | 1000 tokens | 매우 큰 Chunk |

고정 조건:
- `chunk_overlap = 0`
- embedding model은 `text-embedding-3-small`로 고정
- 같은 vector DB 설정 사용
- 같은 검색 방식과 같은 `top-k` 사용
- 같은 평가 질문셋 사용
- 모든 chunk에는 원본 `metadata.id`, `source`, `sourceUrl`, `title`, `published_at`, `category`를 유지

예상:
- B는 세부 문장 검색에는 유리하지만, 신청 대상/기간/방법/문의처가 분리되어 답변 맥락이 깨질 수 있다.
- C와 D가 1차 후보가 될 가능성이 높다.
- E와 F는 문맥 보존에는 좋지만, 한 chunk에 여러 주제가 섞여 검색 정밀도가 떨어질 수 있다.
- A는 baseline으로 필요하지만, 긴 공지에서 검색 초점이 흐려질 가능성이 있다.

## 2차 실험: Chunk Overlap 비교

1차 실험 A-F 중 가장 성능이 좋거나 운영 관점에서 가장 균형 잡힌 chunk size 1개를 선택한다. 그 chunk size를 고정한 뒤 overlap 크기만 바꿔 비교한다.

예시: 1차에서 D_500이 가장 안정적이면 아래처럼 진행한다.

| 실험 | Chunk 크기 | Overlap | 의미 |
| --- | ---: | ---: | --- |
| D-O0 | 500 tokens | 0 tokens | 1차 실험 기준 |
| D-O50 | 500 tokens | 50 tokens | 약한 overlap |
| D-O100 | 500 tokens | 100 tokens | 중간 overlap |
| D-O150 | 500 tokens | 150 tokens | 강한 overlap |

평가 포인트:
- 정답 문서 recall이 올라가는지
- 답변에 필요한 조건/기간/방법이 함께 검색되는지
- 같은 문서의 비슷한 chunk가 top-k를 과도하게 차지하지 않는지
- chunk 수 증가에 따른 embedding 비용과 검색 latency가 감당 가능한지

## 3차 실험: Recursive Character Splitting

재귀적 글자 분할은 문단, 문장, 공백 순서로 자연스러운 경계를 찾아 자르는 방식이다. 단순 token split보다 문장 중간 절단을 줄이는 것이 목적이다.

설정:
- 1차 실험에서 유력한 chunk size 1-2개를 사용한다.
- overlap은 우선 0으로 시작한다.
- 구분자 우선순위는 `\n\n`, `\n`, `.`, `?`, `!`, `다.`, 공백 순서로 둔다.

이 데이터에서 기대하는 장점:
- `se게시판` 공지의 번호 목록과 문단 구조를 덜 깨뜨린다.
- 긴 수업/학적/장학금 공지에서 신청 방법과 유의사항이 문장 단위로 보존된다.
- 에브리타임 강의평처럼 짧은 문서는 대부분 그대로 유지된다.

## 4차 실험: Document Specific Splitting

구조 기반 분할은 출처와 문서 유형에 따라 다른 규칙을 적용한다.

출처별 전략:
- `에브리타임`: 대부분 짧은 강의평이므로 기본적으로 문서 1개를 chunk 1개로 유지한다. 단, 긴 리뷰만 문단 기준으로 분할한다.
- `se게시판`: 제목/출처/분류/작성일 헤더는 모든 chunk에 붙이고, 본문은 번호 목록, 신청 기간, 대상, 방법, 문의처, 유의사항 단위로 나눈다.
- `학과공식사이트`: 소개, 교육목표, 교수진, 진로, 동아리처럼 섹션 의미가 분명하므로 섹션 제목 단위로 나눈다.

카테고리별 전략:
- `수업`, `학적·졸업`, `장학금`: 기간, 대상, 신청 방법, 제출 서류, 문의처가 답변 핵심이므로 절차 단위가 끊기지 않게 한다.
- `비교과·행사`, `연구·캡스톤`, `취업·진로`: 모집 대상, 일정, 신청 링크, 담당자 정보를 한 chunk 안에 보존한다.
- `강의평`: 한 리뷰가 하나의 판단 단위이므로 가능한 한 분할하지 않는다.
- `학생회`, `행정·안내`, `기타`: 문서 길이에 따라 문단 또는 번호 목록 기준으로 나눈다.

## 5차 실험: Semantic Chunking

의미 기반 분할은 고정 길이가 아니라 내용 전환 지점을 찾아 chunk를 나누는 방식이다. 이 데이터에서는 단순히 임베딩 유사도만 보고 자르면 위험하다. 공지사항은 문장이 서로 달라도 같은 절차를 설명하는 경우가 많기 때문이다.

전략:
1. 문서를 문장 또는 짧은 문단 단위로 먼저 나눈다.
2. 각 단위에 대해 embedding을 만들고 인접 단위 간 의미 유사도를 계산한다.
3. 유사도가 급격히 낮아지는 지점을 후보 경계로 잡는다.
4. 단, 아래 항목은 같은 chunk에 묶는 것을 우선한다.
   - 신청 기간 + 신청 방법
   - 지원 대상 + 제외 대상
   - 제출 서류 + 제출처
   - 일정 + 장소
   - 과목명 + 교수명 + 강의평 본문
   - 문의처 + 담당 부서
5. chunk가 너무 작으면 앞뒤 chunk와 병합한다.
6. chunk가 너무 크면 번호 목록이나 섹션 제목을 기준으로 한 번 더 나눈다.

권장 제한:
- 최소 chunk 크기: 120 tokens
- 목표 chunk 크기: 300-600 tokens
- 최대 chunk 크기: 900 tokens

의미 기반 청킹에서 특히 봐야 할 문서:
- 긴 `수업` 공지: 공결신청, 수강신청, 강의평가 안내
- 긴 `학적·졸업` 공지: 교육과정 개편, 졸업 요건
- 긴 `장학금` 공지: 신청 조건, 서류, 기간
- 긴 `연구·캡스톤` 공지: 팀 구성, 일정, 분반, 담당 교수
- `강의평`: 리뷰 하나가 의미 단위로 유지되는지

## 성능 비교 기준

성능 비교는 자동 평가와 사람 평가를 같이 쓴다.

자동 평가:
- `Recall@3`: 정답 문서 또는 정답 chunk가 상위 3개 안에 있는지
- `Recall@5`: 정답 문서 또는 정답 chunk가 상위 5개 안에 있는지
- `MRR@5`: 정답이 몇 번째에 나오는지
- `Context Precision`: top-k에 불필요한 chunk가 얼마나 섞이는지
- 평균 검색 latency
- 총 chunk 수와 embedding token 비용

사람 평가:
- 답변 정확도: 질문에 맞는 답을 했는가
- 근거 충실도: 검색된 문서 내용만으로 답했는가
- 세부 정보 보존: 날짜, 신청 기간, 장소, 대상, 교수명, 과목명, 문의처가 정확한가
- 출처 제시: `sourceUrl` 또는 문서 제목을 제대로 제공하는가
- 답변 완성도: 사용자가 바로 이해하고 행동할 수 있는가

점수 기준 예시:

| 점수 | 기준 |
| ---: | --- |
| 2 | 정확하고 근거가 충분함 |
| 1 | 대체로 맞지만 일부 정보가 부족하거나 애매함 |
| 0 | 틀렸거나 근거가 없음 |

즉, 전부 사람이 매번 점수 매기는 방식은 아니다. 먼저 정답 문서가 정해진 테스트 질문셋을 만들면 retrieval 성능은 자동으로 계산할 수 있다. 다만 최종 RAG 답변의 자연스러움, 근거 충실도, 세부 정보 정확성은 사람이 일부 샘플을 채점하는 것이 가장 안전하다.

- `수업`: 12개

- `장학금`: 8개

- `연구·캡스톤`: 6개

질문 유형:
- 단일 사실 질문: 신청 기간, 장소, 문의처, 담당자
- 절차 질문: 어떻게 신청하는지, 어떤 순서로 해야 하는지
- 조건 질문: 누가 대상인지, 제외 조건은 무엇인지
- 비교 질문: 특정 과목/교수 강의평의 공통 의견

각 테스트 문항은 아래 필드를 가진다.

```json

  "gold_doc_ids": ["kumoh-notice-46084"],
  "gold_category": "행정·안내",
  "expected_evidence": ["신청 방법", "유의사항", "신청 기한"],
  "answer_checkpoints": ["신청 경로", "기한", "유의사항", "출처"]

```

## 실행 순서

오늘 실행:
1. `data/document통합파일(에타리뷰분리).json`을 로드하고 스키마를 확인한다.
2. 1차 A-F no-overlap chunk 파일을 생성한다.
3. 각 실험별 `chunks.jsonl`과 `stats.json`을 저장한다.
4. `text-embedding-3-small`로 각 chunk의 embedding을 생성한다.
5. 각 실험별 embedding 저장 파일 또는 vector index를 생성한다.
6. chunk 수, embedding token 수, 실패 건수, 처리 시간을 기록한다.

다음 단계:
1. 테스트 질문셋과 gold document ID를 만든다.
2. 자동 retrieval 평가로 상위 2개 chunk size 후보를 고른다.
3. 상위 후보에 대해 RAG 답변 샘플을 사람 기준으로 채점한다.
4. 최종 chunk size 후보 1개를 선택한다.
5. 선택한 chunk size로 overlap 2차 실험을 진행한다.
6. Recursive Character Splitting을 비교한다.
7. Document Specific Splitting을 비교한다.
8. Semantic Chunking을 비교한다.
9. 자동 평가와 사람 평가를 합쳐 최종 청킹 방식을 선택한다.
