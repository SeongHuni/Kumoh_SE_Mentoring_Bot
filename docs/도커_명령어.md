# Docker 명령어 정리

이 프로젝트를 돌리면서 실제로 쓴 것만 모았다.
처음 설치하고 실행하는 순서는 [팀원_실행하기.md](팀원_실행하기.md) 에 있다.

모든 명령은 `docker-compose.yml` 이 있는 프로젝트 루트에서 실행한다.

---

## 구성

서비스는 셋이고, `docker-compose.yml` 에 정의돼 있다.

| 서비스 | 포트 | 하는 일 |
| --- | ---: | --- |
| `frontend` | **3000** | 사용자가 여는 화면 (Next.js) |
| `backend` | **8787** | 검색·답변 API (FastAPI) |
| `chroma` | **8000** | 벡터 DB |

브라우저에서 여는 곳은 **http://localhost:3000** 하나다.
API 문서는 http://localhost:8787/docs 에 있다.

컨테이너끼리는 `http://chroma:8000` 처럼 **서비스 이름**으로 서로를 찾고,
브라우저가 호출하는 주소만 `localhost` 다.

---

## 매일 쓰는 것

```bash
docker compose up -d          # 켜기
docker compose ps             # 상태 보기
docker compose down           # 끄기
```

`-d` 는 백그라운드로 띄운다는 뜻이다. 빼면 터미널이 로그에 묶인다.

**코드를 고쳤을 때만** 다시 빌드한다.

```bash
docker compose up -d --build
```

`backend/` 나 `frontend/` 를 고쳤으면 필요하고, 데이터만 바뀌었으면 필요 없다.
처음에는 3~5분 걸리고 그다음부터는 바뀐 부분만 다시 만든다.

---

## 로그 보기

```bash
docker compose logs -f backend      # 실시간 (Ctrl+C 로 나감)
docker compose logs --tail 50 backend
docker compose logs                 # 전체 서비스
```

`-f` 는 계속 따라간다는 뜻이다. 에러를 찾을 때는 이걸 켜두고 질문을 보내본다.

---

## 하나만 다시 시작

```bash
docker compose restart backend            # 재시작
docker compose up -d --force-recreate backend   # 컨테이너를 새로 만들기
docker compose up -d --build backend      # 다시 빌드까지
```

`.env` 나 `docker-compose.yml` 의 환경변수를 고쳤으면 `restart` 로는 반영되지 않는다.
`--force-recreate` 를 써야 한다.

## 상태 확인

```bash
docker compose ps
```

**PORTS 를 반드시 본다.**

```
backend-1    0.0.0.0:8787->8787/tcp     <- 정상
backend-1    8787/tcp                   <- 게시 실패. 접속 안 됨
```

`0.0.0.0:...->` 가 없으면 다른 프로그램이 그 포트를 이미 쓰고 있다는 뜻이다.
컨테이너는 "Up" 이라 알아채기 어렵다. 자세한 건 아래 [막힐 때](#막힐-때) 참고.

서비스가 실제로 응답하는지는 이렇게 본다.

```bash
curl http://localhost:8787/api/health
```

`indexed_chunks` 가 **1549** 여야 한다. 0 이면 `chroma-data` 가 없는 것이다.

## 컨테이너 안에 들어가기

```bash
docker compose exec backend bash        # 셸
docker compose exec backend python -c "import chromadb; print(chromadb.__version__)"
docker compose exec backend ls /app     # 파일 확인
```

이미지에 뭐가 들어갔는지, 환경변수가 제대로 넘어갔는지 확인할 때 쓴다.

```bash
docker compose exec backend env | grep CHROMA
```

## 이미지와 정리

```bash
docker images        # 이미지 목록 (붕어빵 틀)
docker ps            # 실행 중인 컨테이너 (붕어빵)
docker ps -a         # 멈춘 것까지
```

**이미지는 틀, 컨테이너는 그 틀로 찍어낸 실행체다.**
`docker compose down` 은 컨테이너만 없앤다. 이미지는 남아서 다음에 빌드 없이 뜬다.

디스크가 부족하면 정리한다.

```bash
docker image rm <이미지이름>     # 특정 이미지
docker system df                 # 무엇이 얼마나 쓰는지
docker system prune              # 안 쓰는 것 정리 (이미지·네트워크·캐시)
```

`docker system prune` 은 **멈춰 있는 컨테이너와 안 쓰는 이미지를 지운다.**
지금 돌아가는 것은 건드리지 않지만, 다음에 다시 빌드해야 하므로 시간이 든다.

## 데이터는 어디에 있나

`chroma-data/` 는 **호스트 폴더**를 컨테이너에 붙인 것이다(볼륨 마운트).

```yaml
volumes:
  - ./chroma-data:/data
```

그래서 컨테이너를 지워도 데이터는 남는다. 반대로 **폴더를 지우면 데이터가 사라진다.**

`docker compose down -v` 의 `-v` 는 볼륨까지 지운다는 뜻인데,
여기서는 호스트 폴더를 쓰므로 `chroma-data/` 는 그대로 남는다.
그래도 습관적으로 `-v` 를 붙이지 않는 편이 안전하다.

## 막힐 때

### 포트가 이미 쓰이고 있을 때 (가장 흔하다)

`docker compose ps` 의 PORTS 에 `0.0.0.0:...->` 가 없으면 이 경우다.
**Docker 는 이 실패를 조용히 넘어간다.** 컨테이너는 "Up" 이지만 접속이 안 된다.

로컬에서 직접 띄운 것이 원인인 경우가 대부분이다
(`chroma run`, `npm run api`, `npm run dev` 등).

```powershell
# 무엇이 잡고 있는지 (Windows PowerShell)
Get-NetTCPConnection -LocalPort 8787 -State Listen |
  ForEach-Object { Get-Process -Id $_.OwningProcess }

# 끄기
Get-NetTCPConnection -LocalPort 8787 -State Listen |
  ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

끈 다음 다시 만든다.

```bash
docker compose up -d --force-recreate backend
```

### "container name is already in use"

옛 컨테이너가 이름을 붙잡고 있는 경우다.

```bash
docker rm -f chroma se-backend se-frontend
docker compose up -d
```

지금은 `container_name` 을 쓰지 않아서 Docker 가 폴더 이름을 붙여
자동으로 구분한다(`se_rag_chatbot-backend-1`). 옛 컨테이너가 남아 있을 때만 걸린다.

### 폴더 이름을 바꾸려는데 자꾸 되살아난다

컨테이너가 `./chroma-data` 를 물고 있는데 그 경로가 사라지면
Docker 가 **없는 폴더를 다시 만든다.** `restart: unless-stopped` 라 계속 되살아난다.

```bash
docker compose down     # 먼저 완전히 내린다
# 그다음 폴더 이름 변경 (VS Code 도 닫아야 한다)
docker compose up -d
```

폴더 이름이 바뀌면 **이미지 이름도 바뀌어 다시 빌드된다.** Docker 가 폴더 이름을
프로젝트 이름으로 쓰기 때문이다.

### 모든 질문에 "자료에서 확인할 수 없습니다"

`chroma-data` 가 없거나 경로가 한 겹 더 들어간 것이다.

```bash
curl http://localhost:8787/api/health     # indexed_chunks 가 0 이면 이 경우
ls chroma-data/chroma.sqlite3             # 26MB 파일이 있어야 한다
```

### 빌드가 실패한다

```bash
docker compose build --no-cache backend   # 캐시 없이 다시
docker compose logs backend
```

`.dockerignore` 가 필요한 파일까지 막고 있는 경우가 있다.
`COPY` 단계에서 "not found" 가 나오면 거기를 본다.

### 변경이 반영되지 않는다

```bash
docker compose up -d --build --force-recreate backend
```

이미지를 다시 만들고 컨테이너도 새로 찍는다.
그래도 안 되면 캐시 문제다. `--no-cache` 로 빌드한다.

---

## 전부 처음부터 다시

```bash
docker compose down
docker compose build --no-cache
docker compose up -d
```

10분쯤 걸린다. `chroma-data/` 는 호스트 폴더라 그대로 남는다.
