## 2. 최종 발표까지 해야 하는 것

4차 발표 13쪽에서 **시연하겠다고 약속한 4가지** 기준이다.

| # | 약속한 시연 항목 | 현재 상태 | 필요 작업 |
| --- | --- | --- | --- |
| 1 | 실제 질의응답 — 검색 후 답변, 출처 일치 | **완료** | 시연 시나리오만 준비 |
| 2 | 후속 질문 — 대화 맥락 반영 | **미구현** | 대화 이력 + 질의 재작성 |
| 3 | 자주 묻는 질문 캐싱 — 답변 저장·재사용 | **미구현** | 답변 캐시 (지금은 임베딩 캐시만 있음) |
| 4 | 근거 부족 — 근거 없음 안내 | **부분** | 프롬프트 지시만 있고 코드 게이트 없음 |

### 작업 ① 후속 질문 처리 (가장 큼)

`PROMPT_STRATEGY.md`에 설계는 끝나 있다. 구현만 남았다.

- 대화 이력을 담을 세션 구조 (최근 3턴)
- 검색 계획기: 후속 질문 → 독립형 질의로 재작성 (LLM 1회 호출)
- 대상이 불명확하면 `clarify` 반환 → 검색하지 않고 되묻기
- **핵심 원칙**: 검색 계획기만 대화를 읽고, 답변 생성기는 `현재 질문 + 검색 자료`만 받는다

### 작업 ② 답변 캐싱

`scripts/lib/query-cache.js`는 **질문 임베딩**만 캐시한다. 답변 캐시는 없다.

- 같은 질문(정규화 후) → 저장된 답변 재사용
- 시연 포인트는 **응답 시간 비교**이므로 적용 전후 ms를 출력해야 함
- 기존 `query-cache.js`의 파일 캐시 패턴을 그대로 재사용 가능

### 작업 ③ 근거 부족 차단

지금은 프롬프트에 "근거 없으면 모른다고 답하라"고만 적혀 있다. 코드로 막지 않는다.

- 검색 결과 최고 유사도가 임계값 미만이면 **LLM을 호출하지 않고** "확인할 수 없음" 반환
- 임계값은 300문항 데이터로 정한다 (정답 있는 질문 vs 없는 질문의 점수 분포 비교)

### 작업 ④ 프롬프트 개선 루프 (12쪽 약속)

질문 → 실패 기록 → 프롬프트 수정 → 재검증

- 팀원이 던진 질문과 후속 질문 목록 수집
- 오류를 4종으로 분류: 문맥 누락 / 근거 없는 답변 / 잘못된 출처 / 과도하게 긴 답변
- 같은 질문 세트로 수정 전후 비교

### 작업 ⑤ 발표 자료

- 최종 발표 PPT + 대본 (`build-ppt.py` 재사용 가능)
- 시연 시나리오 대본 (질문 순서, 예상 출력)
