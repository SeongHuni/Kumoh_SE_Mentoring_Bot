# 청킹 전략 비교 실험

`documents_clean.json`(850건)을 5가지 방식으로 청킹해서 각각 벡터DB를 만들고, 검색 성능을 비교합니다.

## 파일 구성

```
chunking_strategies.py   5가지 전략 정의
build_dbs.py             5개 Chroma 컬렉션 구축
evalset.json             평가 질문 15개 (정답 검증 완료)
evaluate.py              Recall@K · MRR 측정 및 비교
documents_clean.json     입력 데이터 (850건)
```

## 설치

```bash
pip install chromadb langchain-text-splitters openai
```

## 실행

```bash
# 1. API 키 설정
set OPENAI_API_KEY=sk-...          # Windows
export OPENAI_API_KEY=sk-...       # Mac/Linux

# 2. DB 5개 구축 (한 번만, 약 5~10분)
python build_dbs.py

# 3. 성능 비교
python evaluate.py
```

특정 전략만 다시 만들려면 `python build_dbs.py --only S5_recursive_ko`

## 5가지 전략

| 전략 | 설정 | 청크 수 | 비교 목적 |
|---|---|---|---|
| `S1_nosplit` | 분할 없음 | 850 | **베이스라인** |
| `S2_fixed500` | 고정 500자 / overlap 100 | 1,980 | 작은 청크 |
| `S3_fixed1000` | 고정 1000자 / overlap 150 | 1,195 | 큰 청크 |
| `S4_recursive` | Recursive 800 / 기본 구분자 | 1,659 | 구분자 인식 |
| `S5_recursive_ko` | Recursive 800 / 한국어 구분자 + 헤더 재주입 | 1,530 | 한국어 최적화 |

**설계 의도** — 변인을 하나씩만 바꿔서 각 기법의 순수 효과를 분리했습니다.

- `S2` vs `S3` → **청크 크기**만의 효과
- `S3` vs `S4` → **구분자 인식** 여부의 효과
- `S4` vs `S5` → **한국어 구분자 + 헤더 재주입**의 효과
- 전체 vs `S1` → **애초에 자르는 게 이득인가**

## 평가 방식

### 왜 문서 단위로 평가하는가

전략마다 청크 수가 850~1,980으로 다릅니다. 청크 단위로 평가하면 잘게 쪼갠 전략이 왜곡됩니다. 그래서 **"정답 문서가 상위 K개 청크 안에 등장했는가"** 로 측정합니다.

```
질문: "캡스톤 팀 몇 명?"
검색된 청크 5개 → 각각 어느 원본 문서에서 왔는지 확인
                → 정답 문서(kumoh-notice-49254)가 몇 번째에 나왔는가
```

### 지표

- **Recall@K** — 정답 문서가 상위 K개 안에 있었던 질문 비율
- **MRR** — 정답이 처음 등장한 순위의 역수 평균 (1등=1.0, 2등=0.5, 3등=0.33)

`Recall@5`가 같아도 `MRR`이 높으면 더 앞순위로 찾은 것이므로 우수합니다.

### 출력 예시

```
  전략                 청크수     R@1    R@3    R@5   R@10     MRR
  ──────────────────────────────────────────────────────────────
  S1_nosplit             850   40.0%  66.7%  73.3%  80.0%   0.531
  S5_recursive_ko       1530   46.7%  73.3%  86.7%  93.3%   0.612
```

질문 유형별 정답률과 "어느 전략에서도 못 찾은 질문"도 함께 출력됩니다.

## 평가셋 확장

15개는 실험 시작용입니다. **30~50개까지 늘리면 결과 신뢰도가 크게 올라갑니다.**

```json
{
  "question": "질문 문장",
  "answer_doc_ids": ["정답 문서의 metadata.id"],
  "type": "질문 유형 (사실확인/절차/탐색 등)",
  "note": "정답 근거 메모"
}
```

**만드는 요령** — `documents_clean.json`을 열어 문서를 하나 고르고, "이 문서를 봐야만 답할 수 있는 질문"을 씁니다. 실제 학생이 쓸 법한 표현으로 쓰는 게 중요합니다. 문서에 있는 단어를 그대로 쓰면 검색이 너무 쉬워져서 변별력이 없어집니다.

```
❌ "수강꾸러미 신청 기간이 2026년 7월 22일부터인가요?"   (문서 표현 그대로)
✅ "장바구니 담는 거 언제까지 해야 해요?"                (학생 실제 표현)
```

`type`을 채워두면 "강의평 질문은 어느 전략이 강한가" 같은 분석이 가능합니다.

## 결과 해석 시 주의

**1. 베이스라인(S1)이 이길 수 있습니다**
데이터 중앙값이 632자로 짧은 편이라, 안 자르는 게 최선일 가능성이 실제로 있습니다. 그 결과가 나와도 실패가 아니라 **"이 데이터에는 청킹이 불필요하다"는 유의미한 발견**입니다.

**2. 15개 질문으로는 1~2%p 차이를 신뢰할 수 없습니다**
질문 1개가 6.7%p입니다. 격차가 10%p 이상 나야 의미 있는 차이로 볼 수 있고, 그보다 작으면 평가셋을 늘려서 재측정해야 합니다.

**3. 모든 전략이 실패한 질문을 보세요**
이건 청킹 문제가 아닙니다. 데이터에 답이 없거나, 임베딩·검색 방식 자체를 개선해야 하는 신호입니다.

## 비용

전체 약 7,200청크 임베딩 + 질문 75회 검색 기준으로 `text-embedding-3-small`은 대략 100원 내외입니다. DB는 `chroma_db/` 폴더에 저장되어 재실행 시 재사용됩니다.
